# 진짜양말 — 카테고리 불러오기 누락 + 미리보기 개수 부정확 수정

## 배경

진짜양말(site 16, 카페24)에서 "양말선물세트" 바로 다음에 있는 "신발"과 "업데이트" 카테고리가 "카테고리
불러오기"/"몰 구조 파악" 양쪽에서 계속 빠졌다. 원인을 좁혀가는 과정에서 서로 다른 세 가지 문제를 순서대로
발견·수정했다.

## 수정 1 — 이미지뿐인 메뉴 항목이 통째로 버려지던 문제

실제 페이지 확인: "신발"/"업데이트"는 `<a href="...cate_no=381"><img src="menu_21.gif" alt=""/></a>`처럼
텍스트가 전혀 없는 이미지 스프라이트 메뉴 항목이었다(같은 페이지의 다른 메뉴 영역은 정상 텍스트라 그쪽
13개는 항상 잘 잡혔음). `scanCategoryMenu`의 `buildPaths`는 `li.textContent`가 비어있으면
(`isMeaningful` 실패) 그 항목을 그냥 버렸다.

`lib/scraper.ts`: `scanCategoryMenu`가 이제 `{ links, textlessHrefs }`를 돌려준다 — 이름을 못 지은
리프 항목의 href를 `textlessHrefs`에 모아둔다. `discoverCategoryLinks`/`sampleMallProfile`(몰 구조 파악)
양쪽에서, 텍스트 메뉴로 카테고리를 이미 몇 개 찾았어도 `textlessHrefs`가 있으면
`discoverCategoriesByVisitingLinks`로 실제 방문해 브레드크럼에서 이름을 채운다.

## 수정 2 — 1차 스캔이 0개일 때 쓰던 폴백의 15개 제한

수정 1 적용 후에도 "신발"만 계속 빠지는 게 재현됐다. 로그로 추적: 이번엔 `scanCategoryMenu`의 텍스트
스캔 자체가 0개로 나와("몰이 자동화 요청을 감지해 축소 응답을 준 것으로 추정" — 아래 "남은 문제" 참고),
`discoverCategoryLinks`/`sampleMallProfile`이 0개 케이스에서 무조건 `findCategoryLinkCandidates`(카테고리
메뉴 영역의 모든 링크를 텍스트 유무와 무관하게 담지만 **15개 제한**)부터 썼다. "신발"은 메뉴 안에서
16번째 링크라 이 제한에 걸려 잘렸다 — 바로 위에서 수집한, 제한이 없는 `textlessHrefs`가 있는데도 안
쓰고 있었다.

**수정**: 0개 케이스에서도 `textlessHrefs`가 있으면 그걸 먼저 쓰고, 완전히 비어있을 때만
`findCategoryLinkCandidates`를 최후수단으로 쓰도록 순서를 바꿨다(두 호출 지점 모두).

## 수정 3 — 미리보기 카테고리 개수: 비상품 UI 아이콘이 상품으로 잡히던 문제

"신발"/"양말선물세트"의 미리보기 개수가 실제(1~6개)보다 100개(정확히 50페이지 한도 × 페이지당 2개)로
부풀려졌다. 실제로 빈 페이지를 열어보니, `#contents` 안에 있는 페이지네이션 이전/다음 화살표・검색・
비교 버튼(`<a href="#none"><img></a>`, `<a href="#SelectSearch"><img></a>`)이 있었다.
`countProductsOnPage`/`countProductsFromHtml`의 "일반 폴백" 스캔(플랫폼 전용 셀렉터가 안 맞을 때 씀)은
`#contents` 스코프 + 위젯 제외만 걸고 **상품 상세 URL 패턴 검사가 없어서** 이 아이콘들을 상품으로 셌다.
게다가 href가 `#none`처럼 프래그먼트뿐이라 실제로는 `page=N`이 포함된 절대경로로 resolve돼 페이지마다
값이 달라져, "반복 감지"(같은 내용이면 멈춤) 안전장치도 못 걸렸다 — 그래서 매 페이지 "새 상품 2개"로
계속 오판해 50페이지 한도까지 다 채웠다.

실제 스크랩(수집) 쪽의 같은 폴백(`scanForProducts`)은 원래부터 상세 URL 패턴을 적용하고 있어 이 문제가
없었다 — 미리보기 쪽만 빠져 있었다.

**수정**: `countProductsOnPage`/`countProductsFromHtml`의 폴백에도 알려진 플랫폼의 상품 상세 URL
패턴(`detailRe`) 필터를 추가했다.

## 수정 4 — 지수+이분 탐색이 "빈 페이지" 신호 한 번만 믿던 문제

수정 3 적용 후, "업데이트" 카테고리(실제 1646개: 240개씩 6페이지+206개)가 미리보기에서 1200개(5페이지에서
멈춤)로 나왔다. 실제 페이지를 다시 열어 손으로 알고리즘을 재현해보면 정확히 1646을 찾아내므로 로직
자체는 맞다 — 탐색 도중 특정 페이지 요청이 일시적으로 빈 응답을 준 것을 "진짜 마지막 페이지"로 그 자리에서
확정해버린 것으로 보인다(이 몰에 오늘 반복 요청을 많이 보내 계속 불안정한 응답을 겪은 것과 같은 계열).

**수정**: `findRealLastPage`에서 "이 페이지가 비었다"는 신호가 나오면 같은 페이지를 한 번 더 확인하고,
두 번 다 비어야만 진짜 끝으로 믿도록 `confirmedEmpty()`를 추가했다(지수 확장/이분 탐색 두 루프 모두 적용).

## 남은 문제 — 이 몰의 자동화 요청 대응 자체가 불안정함

오늘 진짜양말에 수십 차례 자동 요청(카테고리 스캔·미리보기)을 보낸 뒤로, 순수 텍스트 카테고리("남자양말"
등, 원래도 항상 잘 잡히던 것)까지 무작위로 빠지는 증상이 재현됐다 — 코드 문제가 아니라 몰(또는 앞단
CDN/방화벽)이 반복되는 자동화 트래픽을 감지해 축소된 응답을 주는 것으로 추정된다. 수정 1~4는 모두
"몰이 정상 응답할 때" 발생하던 실제 코드 버그를 고친 것이고, 이 마지막 불안정성은 요청 속도를 늦추는 등
접근 방식 자체를 다시 봐야 하는 별개 문제로 남겨뒀다.

## 상태

**구현 완료(수정 1~4).** tsc/eslint 클린. 수정 1~3은 라이브 API 호출로 직접 검증(수정 3은 실제 페이지
HTML을 다시 열어 원인 확인). 수정 4는 알고리즘을 실제 페이지 데이터로 손으로 재현해 로직이 맞음을
확인했으나, 실제 재발 방지 여부는 이 몰이 다시 정상 응답할 때 라이브로 확인 필요.
