# 화면으로 파악한 카테고리 ↔ 최종 결과 대조 리포트

## 요구사항 (사용자 지시 원문, 2026-09-13)

> 내가 사용자가 화면을 통해 카테고리를 파악하듯이 하라고 했잖아. 즉 화면을 통해 카테고리를 파악했으면,
> 마지막 결과가 그 화면의 카테고리와 맞는지, 안맞는건 어떤건지 왜 그런지 등을 피드백 줄 수 있게 해야지.

발단: 투비즈온 메뉴에는 "뷰티", "바디/헤어"가 분명히 보이는데 PTP 카테고리 목록(32개)에는 없다는 신고.

## 그때까지의 문제 — 화면 인식이 "여는 데"만 쓰이고 검증에는 안 쓰였다

2026-09-12에 들어간 화면 인식(비전)은 두 가지에만 썼다: ① "전체 카테고리" 트리거 위치 찾기
(`detectCategoryMenuTriggerFromScreenshot`) ② 그 화면에 대분류 그룹이 몇 개 보이는지 세기
(`detectVisibleCategoryGroupCount`). **그 화면에 무엇이 보였는지를 이름 단위로 남기지 않아**, 최종
결과와 대조할 근거 자체가 없었다.

게다가 결과에서 카테고리가 빠지는 경로에 기록이 없었다. `expandCategoryHubs`(카테고리 하위구조 확인)는
아래 두 경우 카테고리를 **최종 목록에서 완전히 뺀다**:

- 게시판/마이페이지 경로(`NON_CATEGORY_PATH_RE`)
- **상품 0개 + 하위메뉴 0개 + 정렬 위젯 없음** → "빈 허브"로 판단(2026-08-30 소꿉노리 사고 대응으로 도입)

그런데 로그는 8초 이상 걸린 항목만 남기고 있었다(`logIfSlow`). 빠르게 제외된 카테고리는 **로그 한 줄
없이** 사라져, "왜 없지?"에 답할 방법이 없었다. 실제로 이번 신고에서 투비즈온은 탐지 단계에서 51개를
찾았는데 최종 32개만 남았고, 19개가 어디서 왜 빠졌는지 추적할 근거가 전혀 없었다.

## 구현

1. **화면에서 카테고리 이름 읽기** — `lib/ai.ts`에 `detectVisibleCategoryNames()` 추가(Groq 비전 →
   Ollama 비전 순, 기존 비전 함수들과 같은 폴백 구조). 메뉴가 열린 바로 그 화면에서 사람이 카테고리로
   읽는 이름을 전부 받아온다. 응답 형태가 보장되지 않아 `sanitizeVisibleCategoryNames()`로 정리한다
   (문자열 아닌 항목/40자 초과/중복/공백 정리, 300개 상한).
2. **캡처 시점** — 두 탐지 경로 모두 "메뉴가 열려 있고 그 결과를 채택한" 순간에 캡처한다.
   - 화면 인식 경로: 이미 완전성 검사용으로 찍어둔 스크린샷을 그대로 재사용(추가 캡처 없음).
   - 헤더 전수클릭 경로: 후보를 채택할 때마다 그 시점 화면을 보관했다가, 루프가 끝난 뒤 최종 채택된
     화면 하나만 비전에 넘긴다(루프가 끝나면 페이지를 다시 불러온 상태라 재현이 불가능하다).
3. **제외 사유 수집** — `expandCategoryHubs`가 `excluded: {name, href, reason}[]`을 같이 돌려준다.
   제외는 항상 로그로도 남긴다(`[허브확장:제외:몰이름] "이름" — 사유`). 확장 단계 요약도 한 줄
   추가(`최상위 51개 → 최종 32개(하위 펼침/제외 N개/중복제거 반영)`).
4. **대조** — `buildCategoryScreenCheck(screenNames, finalLinks, excluded)`(순수 함수):
   - `missing`: 화면엔 있는데 결과엔 없는 것 + 사유(제외 기록이 있으면 그 사유, 없으면 "탐지 단계에서
     못 찾음" — 어느 단계를 봐야 하는지가 갈린다)
   - `extra`: 결과엔 있는데 화면에서 못 읽은 것(비전이 놓쳤거나 스크롤 밖일 수 있어 참고용)
   - 이름 비교는 `normalizeCategoryName()`으로 정규화한다 — 결과는 "대분류 > 중분류" 경로로 저장되고
     비전은 화면의 마지막 이름만 읽으므로 경로의 마지막 조각끼리 비교하고, 공백/구분자 차이를 흡수한다.
   - **화면 인식 결과가 없으면 `null`** — 근거 없이 "누락"이라고 단정하지 않는다.
5. **화면 표시** — 몰 구조분석 결과 카드에 블록 추가. 전부 일치하면 초록색 한 줄, 빠진 게 있으면
   항목별로 `· 뷰티 — 이 페이지에 상품도, 하위 메뉴도, 정렬 위젯도 없어 상품 목록 페이지가 아니라고 판단`
   처럼 **무엇이 왜 빠졌는지** 보여준다(최대 12개 + "외 N개").

## 곁들여 고친 것 — 로그아웃 상태에서 카테고리가 통째로 사라지던 문제

"상품 0개 + 하위메뉴 0개 + 정렬 없음"은 **로그인이 풀린 회원전용 몰의 화면과 구분이 안 된다.**
투비즈온은 로그인 없이는 상품은 물론 카테고리 메뉴조차 렌더링되지 않는 몰이라(익명 HTML에 '패션의류'
문자열조차 없음), 세션이 흔들린 실행 하나가 멀쩡한 카테고리를 목록에서 지워버릴 수 있었다. 그래서
배제 직전에 그 페이지의 로그인 상태를 확인해, **확장 시작 시점엔 로그인돼 있었는데 지금 화면이 로그아웃
상태로 보이면 배제하지 않고 그대로 둔다**(`[허브확장:유지:…]`로 로그에 남긴다). 로그인이 필요 없는
몰은 시작 시점 로그인 신호 자체가 없어 이 분기를 타지 않으므로, 기존 "빈 허브 배제"(게시판 글 오탐
방지)는 그대로 유지된다.

## 후속 — 누락분 자동 재검증(되살리기)과 노이즈 제거 (2026-09-13, 같은 날)

사용자 지시: "사람이 보는 화면에는 모든 카테고리가 확인이 된다. 그 기준으로 누락된 카테고리가 있을
경우 **다른 방법으로라도 다시 해당 카테고리를 검증하는 프로세스**를 넣어."

대조해서 "빠졌다"고 알려주는 것까지로는 부족하다는 것 — 빠졌으면 되살려야 한다.

### 1. 늦게 그려지는 목록 대응 (`countProductsSettled`)

1차 판정이 틀린 진짜 원인이 여기였다. `countProductsOnPage`는 호출 순간의 DOM만 보는 스냅샷인데
페이지 이동 직후 한 번만 세고 확정했다. 실사용 로그(2026-09-13, 투비즈온): 51개 중 **32개**가
"상품 0개"로 배제됐고 살아남은 것들은 하나같이 "상품 5개"였다. 수정 후 같은 페이지들이
`첫 스냅샷 5개 → 2.0초 기다린 뒤 25개`로 잡힌다 — 5개는 먼저 그려지는 추천 위젯이었다.

- 개수가 **더 이상 늘지 않을 때까지** 센다(0.5초 간격, **최소 2초 관찰**, 최대 6초).
- 최소 관찰 시간이 핵심이다 — 처음엔 "한 번 더 세서 안 늘면 끝"으로 만들었다가, 합성 페이지 실측에서
  5개가 이미 있는 페이지를 0.5초 만에 확정해 1.5초 뒤 오는 40개를 그대로 놓치는 걸 발견했다.
- 허브 확장뿐 아니라 **표본검증**(`looksLikeRealCategoryBatch`)에도 적용했다 — 거기서 잘못 판단하면
  찾아둔 카테고리 묶음 전체가 버려져 피해가 더 크다.

### 2. 누락 카테고리 재검증 (`recoverMissingCategories`)

화면 대조에서 빠진 항목이 나오면 이어서 자동 실행된다.

1. **URL 확보** — 화면에서 이름만 읽은 카테고리는 방문할 주소를 모른다. 그래서 메뉴가 열린 화면의
   링크 목록을 스크린샷과 **같은 순간에** 모아두고(`CategoryMenuDiscovery.menuLinks`), 이름으로 찾는다
   (`resolveMissingCategoryCandidates`: 1순위 제외 기록의 href, 2순위 메뉴 링크).
2. **더 끈질긴 재방문** — 1차와 달리 `load`까지 기다리고 개수가 안정될 때까지 지켜본다.
3. **눈으로 확인** — 그래도 0개면 화면을 캡처해 비전에게 "사람이 보기에 상품 목록이 있느냐"고 묻는다
   (`detectProductListVisible`). DOM 셀렉터가 못 읽는 것과 상품이 없는 것은 다른 문제다.
4. 되살아난 카테고리는 최종 목록에 다시 넣고, 근거(`재방문에서 상품 25개 확인` /
   `화면 인식으로 상품 목록 확인`)를 화면에 같이 보여준다.

### 3. 대조 노이즈 제거

첫 실사용에서 "누락 39개 → 13개"까지 줄어든 뒤, 남은 13개를 보니 **진짜 누락이 하나도 없었다**:

- **대분류 탭 이름 7개**(패션의류/잡화/뷰티, 휴대폰/디지털/가전, 생활/식품/건강, 출산/육아,
  가구/인테리어, 스포츠/레저, 자동차/공구/산업) — 그룹 제목이라 저장 대상이 아니다. 링크가 없어
  재검증 후보조차 못 되므로, 그 점을 근거로 "대분류 탭(그룹 제목)으로 보임 — 정상"으로 사유를 바꾼다.
- **비전 오독 5개** — `천구/커튼`(침구/커튼), `유아동류`(유아동의류), `주얼리/시계`(쥬얼리/시계),
  `취미/니스/수영`(휘트니스/수영). 이미 결과에 있는 카테고리를 "없다"고 알리는 오보였다.
  `findApproximateMatch`(편집거리 기반, 이름 길이에 따라 허용치 1~2)로 흡수한다 — 짧은 이름은
  한 글자 차이도 다른 카테고리일 수 있어 허용치를 0으로 둔다("신발" vs "실발").

### 실사용 결과 (2026-09-13, 투비즈온)

| | 수정 전 | 수정 후 |
| --- | --- | --- |
| 허브 확장 | 51개 → **19개**(32개 배제) | 51개 → **50개**(1개 배제) |
| 재검증 | 없음 | 1개 되살림(PC주변기기, 재방문에서 상품 25개) → **확인 안 되는 것 0개** |
| 저장된 카테고리 | 32개 | **51개** — "뷰티", "바디/헤어" 포함 |
| 화면 대조 누락 | 39개 | **6개 — 전부 대분류 탭(그룹 제목), "정상"으로 표시** |

노이즈 제거까지 반영한 마지막 실행의 최종 상태(DB 확인): 화면에서 읽은 55개 중 결과에 없는 것 6개이고
그 6개는 모두 `화면의 대분류 탭(그룹 제목)으로 보임 — 링크가 없어 카테고리로 저장하지 않습니다(정상)`.
비전 오독 5개(천구/커튼·유아동류·주얼리/시계·취미/니스/수영·화장품/세제)는 근사 매칭으로 흡수돼 더 이상
누락으로 보고되지 않는다. **진짜 누락 0개.**

조사 중 겪은 혼동 하나를 남겨둔다 — 실행이 끝나기 전에 DB를 조회하면 이전 실행의 `categoryScreenCheck`가
그대로 보인다(`applyProfileResult`의 UPDATE는 분석이 다 끝난 뒤 한 번에 일어난다). 그 중간 스냅샷을
최종 결과로 착각해 "코드가 안 먹었다"고 한참 파고들었다. 결과를 확인할 땐 `[누락재검증:…] 되살린 …`
로그가 찍힌 뒤에 조회할 것.

## 검증

- `tsc` / `lint` / 단위테스트 287개 통과(신규 `tests/unit/categoryScreenCheck.test.ts` 10개 —
  예시 기반 + fast-check 속성 테스트).
- **실제 비전 호출로 확인**: 투비즈온 메뉴 구조를 그대로 본뜬 화면을 실제 크롬으로 렌더링해 캡처 →
  `detectVisibleCategoryNames`가 **8개(여성의류·남성의류·언더웨어·신발·가방/잡화·쥬얼리/시계·뷰티·
  바디/헤어)를 전부 읽어냄** — 사용자가 누락됐다고 지적한 "뷰티"/"바디/헤어"가 화면 기준으로는 정확히
  잡힌다는 뜻이라, 다음 실행부터 이 둘이 결과에 없으면 사유와 함께 화면에 뜬다.
- **아직 확인 못 한 것**: 실제 투비즈온 몰 구조분석을 다시 돌렸을 때 이 대조 블록에 무엇이 찍히는지
  (그게 "뷰티가 왜 빠졌나"의 최종 답이 된다). 실행에 10분 이상 걸려 이번 세션에서는 안 돌렸다.
