# 고객 스크래핑 요청 포털 — 기본 분석/설계 검토

개발 지시가 아니라 **검토 문서**입니다. 2026-08-30 사용자 설명을 근거로 기본 분석/설계 수준만
정리했습니다 — 실제 구현은 별도 착수 시점에 이 문서를 다시 검토·구체화해야 합니다.
[[external-service-readiness]](대외 서비스화 준비 검토)의 후속으로, 그 문서가 지적한 문제 중
상당수가 이번 사업 모델 설명으로 실제로는 해소된다는 점부터 짚고 시작합니다.

## 0. 사용자가 설명한 모델 요약과, 이게 왜 중요한 결정인지

정리하면 이런 흐름이다.

1. 고객(특정 몰의 ID/PW를 보유한 거래처)이 **PTP가 아니라 별도의 "서비스요청 온라인 사이트"**에
   가입/로그인한다.
2. 그 사이트에서 고객이 직접 거래처/몰 정보(몰 URL, 로그인 ID/PW 포함)를 입력하고, 컴플라이언스
   책임이 고객에게 있다는 약정에 동의하면 → 당사와의 거래/계약 관계가 확정된다.
3. 고객이 원하는 스크래핑 형태(어떤 몰, 어떤 카테고리, 어떤 데이터 항목/포맷)를 그 사이트를 통해
   전달한다.
4. **당사(운영자, 즉 지금 PTP를 쓰는 사람)가 그 요청을 근거로 PTP로 실제 스크래핑을 수행**한다 —
   PTP 자체는 여전히 운영자만 쓰는 내부 도구다.
5. 결과물(고객이 원한 데이터/포맷)을 당사 웹(포털)에 등록한다.
6. 고객에게 이메일/문자/카카오 알림톡으로 완료를 통지한다.
7. 고객이 알림을 보고 포털에 들어가 **다운로드와 동시에 과금 결제**를 진행한다.

**이 모델을 택하면 이전 검토 문서의 가장 어려운 두 문제가 사실상 사라지거나 성격이 완전히
바뀐다** — 그래서 이 결정은 단순한 "UI를 하나 더 만드는" 문제가 아니라, 이전 문서가 "제품 전략
결정이 먼저 필요하다"고 지적했던 바로 그 결정이 이미 내려진 것과 같다.

- **멀티테넌시 문제(이전 문서 3절, "매우 높음")가 대부분 사라진다** — PTP 자체를 고객에게 직접
  노출하지 않으므로, `sites`/`mall_products`/`product_master`를 테넌트별로 격리할 필요가 없다.
  PTP는 지금처럼 운영자 한 명(또는 소수 내부 직원)이 쓰는 백오피스로 남아도 된다. 테넌트 격리가
  필요한 건 PTP가 아니라 **신규 포털의 "고객 계정별 요청/결제/파일" 데이터**뿐이고, 이건 처음부터
  새로 설계하는 시스템이라 훨씬 다루기 쉽다.
- **로그인필수 몰 제약(이전 문서 1절)의 성격이 바뀐다** — 고객이 자기 브라우저에서 직접 로그인하는
  모델이 아니라, **고객이 준 ID/PW로 운영자가 대신 로그인해 대행 처리**하는 모델이다. 이건 이전
  문서가 "(c) 인건비를 감수하는 대행 운영 모델"이라고 이름 붙였던 선택지를 그대로 채택한 것 — 즉
  스크래핑 자체는 여전히 사람(운영자)이 PTP 화면에서 로그인 창을 열고 확인하는 절차가 남는다.
  자동화되는 건 "요청 접수 → 알림 → 결제"이지 "로그인이 필요한 스크래핑 실행" 그 자체가 아니다.
  이 전제를 착각하면 안 된다 — 아래 3절에서 다시 다룬다.

## 1. 전체 흐름을 상태머신으로 정리

사용자가 설명한 흐름을 "요청(Request)"이라는 하나의 엔티티가 거치는 상태 전이로 표현하면 아래와
같다. 실제 이름은 자유지만, 이렇게 상태를 명시적으로 갖는 설계가 나중에 "지금 몇 건이 어느
단계에서 밀려있는지" 운영 관점에서 반드시 필요해진다.

```
[가입/로그인] → [약정 동의 완료] → [거래관계 확정]
      │
      ▼
[요청 접수](몰/카테고리/원하는 데이터 항목 지정)
      │
      ▼
[검토중] ── (운영자가 요청 내용 확인, 견적/가능 여부 판단) ──▶ [반려/보류]
      │ 승인
      ▼
[처리중](운영자가 PTP로 실제 스크래핑 수행)
      │
      ▼
[산출물 등록](고객이 원하는 포맷으로 가공한 결과를 포털에 업로드)
      │
      ▼
[완료 알림 발송](이메일/SMS/카카오 알림톡)
      │
      ▼
[다운로드 대기] ── 고객이 포털 접속 ──▶ [결제] ──▶ [다운로드 가능] ──▶ [종료/보관만료]
```

몇 가지 설계상 반드시 짚어야 할 지점:

- **"검토중" 단계가 반드시 있어야 한다** — 고객이 입력한 요청이 기술적으로 가능한지(예: 이
  몰이 봇 차단이 심하거나, 원하는 데이터 항목이 그 몰 페이지에 아예 없는 경우) 운영자가 먼저
  판단해야 한다. 이걸 생략하고 바로 자동 접수→자동 처리로 가면, 처리 불가능한 요청이 그대로
  큐에 쌓여 고객에게 "안 된다"는 답을 늦게 주게 된다.
- **"다운로드와 동시에 결제"의 실무적 순서는 재검토가 필요하다** — 문자 그대로 "다운로드 버튼을
  누르면 결제창이 뜨고, 결제가 성공해야 실제 파일이 내려가는" 흐름(선결제 후 다운로드)이 안전하다.
  반대로 다운로드를 먼저 주고 결제를 나중에 하게 하면 미수금·환불 분쟁 리스크가 생긴다. "동시에"라는
  표현을 UX상 자연스럽게 보이게 하되(버튼 하나로 이어지는 느낌), 서버 로직상으로는 **결제 성공 콜백을
  받은 뒤에만 다운로드 링크를 활성화**하는 순서로 설계할 것을 권장한다.
- **거래관계 확정과 요청 접수를 분리했다** — 사용자 설명대로면 "약정 동의=거래관계 확정"과
  "몰별 스크래핑 요청"은 서로 다른 시점에 반복될 수 있는 별개의 일이다(한 번 거래관계를 맺은
  고객이 이후 여러 몰/여러 건을 반복 요청). 이 둘을 같은 화면/같은 절차로 묶으면 재요청이 매번
  약정 동의부터 다시 밟아야 하는 불편이 생긴다 — 계약은 1회, 요청은 N회라는 관계로 설계.

## 2. 필요한 신규 구성요소

### 2-1. 고객 포털(신규 웹앱)

PTP와는 **별도의 애플리케이션**으로 만드는 것을 권장한다(같은 코드베이스 안에 라우트만 추가하는
방식도 기술적으로는 가능하지만, 대외 노출 표면과 내부 운영 도구를 같은 배포 단위에 두면 보안 사고
시 영향 범위가 같이 커진다). 필요한 화면:

- 고객 회원가입/로그인 (PTP의 `lib/auth.ts`와는 별개의, 고객용 인증 체계 — 이메일 인증, 비밀번호
  재설정 등 일반적인 고객용 계정 기능이 필요. PTP의 세션 구현을 참고는 하되 그대로 재사용하지 않는
  편이 안전 — PTP 세션은 내부 admin/user 2단계만 상정하고 만들어졌다)
- 거래처/몰 정보 등록 폼 — 몰 URL, 로그인 ID/PW(반드시 서버에서 암호화 저장), 담당자 연락처(알림
  발송 대상)
- 약정(이용약관) 동의 플로우 — 아래 3절에서 상세
- 스크래핑 요청 작성 폼 — 몰 선택, 원하는 카테고리/데이터 항목, 원하는 산출 포맷(엑셀 등), 특이
  요청사항 자유입력
- 요청 목록/상태 조회 (지금 어느 단계인지)
- 완료된 요청의 다운로드+결제 페이지
- (선택) 과거 요청/결제 내역, 세금계산서 등 정산 관련 화면

### 2-2. 요청(주문) 관리 — 운영자 쪽 화면

운영자가 신규 포털로 들어온 요청을 확인하고 처리 상태를 갱신할 화면이 필요하다. 두 가지 설계
선택지가 있다.

- **(A) 완전 분리형**: 포털의 요청 관리 화면과 PTP는 코드/DB가 분리돼 있고, 운영자가 포털에서
  요청 내용을 확인 → PTP를 열어 직접 몰 등록/스크래핑을 수행 → 다 되면 포털로 돌아와 산출물을
  업로드하고 상태를 "완료"로 바꾸는, 사람이 두 시스템을 오가며 손으로 잇는 방식.
- **(B) 연동형**: 포털의 "요청"이 생성되면 PTP의 `sites`/`clients`에 필요한 레코드가 자동으로
  같이 만들어지고(예: 신규 API 라우트 하나), 운영자는 PTP 화면에 새로 생긴 "고객 요청함" 같은
  뷰에서 바로 처리한다.

**초기엔 (A)를 권장한다.** 이유: 요청 건수가 아직 적을 때는 자동 연동을 만드는 비용이 손으로
옮기는 비용보다 크고, 어차피 로그인필수 몰은 사람이 PTP 화면에서 로그인 창을 열어 확인하는 절차가
필수라(0절 참고) 완전 자동화의 이득이 처음부터 크지 않다. 요청 건수가 늘어나 반복 작업 부담이
커지는 시점에 (B)로 넘어가는 게 현실적이다.

### 2-3. 산출물 생성/보관

PTP에는 이미 스크래핑 결과를 엑셀로 내려받는 기능(`components/panels/shared/StagingItemsGrid.tsx`
쪽의 "옵션 컬럼 고정 위치 + 엑셀 다운로드 WYSIWYG")이 있다 — 이걸 그대로 재사용하거나 응용해
"고객이 요청한 포맷"에 맞춘 산출물을 만드는 경로로 쓸 수 있다. 다만:

- 산출물 파일을 어디에 보관할지(로컬 디스크/오브젝트 스토리지), 얼마나 보관할지(다운로드 후
  N일 뒤 삭제 등 보존기간 정책), 결제 전엔 접근이 차단되는지(서명된 임시 URL + 만료시간, 또는
  서버측 권한 체크)를 설계해야 한다.
- 서로 다른 고객이 원하는 데이터 항목/포맷이 제각각일 수 있다는 전제라면, "이 요청은 어떤 컬럼을
  어떤 이름으로 내보내야 하는지"를 요청 단계에서 구조화된 값으로 받아둬야 나중에 자동화하기
  쉽다(자유 텍스트로만 받으면 매번 사람이 해석해야 함).

### 2-4. 알림 발송(이메일/SMS/카카오 알림톡)

세 채널 모두 **외부 서드파티 연동과 사전 준비 절차**가 필요하다 — 이번 검토에서 가장 리드타임이
길 수 있는 부분이라 미리 인지해둘 것.

- 이메일: SMTP 서비스(또는 SES 등) 계정만 있으면 비교적 빠르게 가능.
- 문자(SMS/LMS): 국내 문자 발송 대행 서비스(알리고, 네이버클라우드 SENS 등) 계정 개설 + 발신번호
  사전등록(통신사 심사) 필요.
- 카카오 알림톡: **정보성 메시지만 허용**(광고성은 별도 수신동의 필요), 카카오 비즈니스 채널 개설
  + 알림톡 템플릿을 사전에 심사받아야 함(템플릿 문구를 임의로 바꾸면 재심사) — 세 채널 중 준비
  기간이 가장 길다. MVP 단계에서는 이메일/문자만으로 시작하고 알림톡은 다음 단계로 미뤄도 무방.

### 2-5. 결제/과금

- 국내 PG사(토스페이먼츠, 이니시스, 나이스페이 등) 가맹 계약이 필요하고, **통신판매업 신고** 등
  전자상거래 관련 사업자 요건을 먼저 확인해야 한다(이미 사업자 등록이 되어 있다면 통신판매업 신고만
  추가하면 되는 경우가 많음 — 정확한 요건은 법률/세무 자문 권장).
  카카오 알림톡용 비즈니스 채널을 만들 때도 사업자 인증이 필요하니 이 부분과 같이 준비하면 된다.
- 과금 기준(건당 정액/데이터 건수 비례/몰 난이도별 차등 등)을 요청 단계에서 미리 계산해 고객에게
  보여줄지("견적 확인 후 진행"), 아니면 산출물이 나온 뒤에야 최종 금액이 확정되는지도 정해야 한다 —
  전자가 고객 경험상 더 좋지만, 스크래핑량을 미리 정확히 예측하기 어려운 몰이 있다면 "예상 금액
  범위"로 안내하고 사후 정산하는 절충안도 가능하다.
- 환불 정책(고객이 원한 데이터가 실제로 없어서 산출물이 부실한 경우 등)을 약정에 명시해야 한다.

## 3. 컴플라이언스/약정 설계

사용자가 이미 "고객 책임의 약정 확인"을 거치는 구조로 설계했다는 점은 이전 검토 문서(3절 "스크래핑
자체의 법적/정책 리스크")가 지적한 가장 큰 리스크를 정면으로 해결하려는 올바른 방향이다. 다만
"약정을 받는다"는 것 자체를 실무적으로 얼마나 탄탄하게 만드는지가 실제 법적 효력을 좌우한다.

- **동의 기록의 증빙력**: 단순히 체크박스만 누르게 하지 말고, **어떤 버전의 약관에, 언제, 어느
  계정이, 어느 IP에서 동의했는지**를 서버 로그로 남겨야 한다(약관 문구를 나중에 바꾸면 "그때 동의한
  버전"을 재현할 수 있어야 분쟁 시 증빙이 된다).
- **약정에 반드시 담을 내용(예시, 실제 문구는 법률 검토 필요)**:
  - 고객은 등록하는 몰 계정에 대해 실제 사용 권한이 있음을 진술·보증한다.
  - 수집된 데이터의 활용(2차 판매/등록 등)에 대한 책임은 고객에게 있다.
  - 개인정보가 포함된 데이터(구매후기 작성자명 등)가 섞여 나올 수 있음을 고지하고, 그 처리 책임
    소재를 명시한다.
  - 당사는 고객이 제공한 로그인정보를 해당 스크래핑 목적으로만 사용하며, 목적 달성 후(또는 일정
    기간 후) 파기한다는 보관/파기 정책.
- **개인정보보호법상 "위탁" 이슈**: 고객의 몰 로그인정보를 당사가 보관·사용하는 구조는 실질적으로
  "타인의 계정정보를 위탁받아 처리"하는 관계에 가깝다 — 표준적인 이용약관 동의만으로 충분한지,
  별도의 위탁계약서 형태가 필요한지는 법률 자문을 받는 것을 권장한다. 이 문서는 법률 자문을
  대체하지 않는다.

## 4. 보안/데이터 흐름 설계 시 주의점

- **몰 ID/PW 저장**: 고객이 포털에 직접 입력하는 값이므로, 포털 서버에서 암호화해 저장해야 한다.
  PTP가 이미 갖고 있는 `encryptSecret`/`decryptSecret`(AES-256-GCM) 방식을 참고할 수는 있지만,
  이전 검토 문서(2절)가 지적했듯 PTP는 지금 **키 하나로 로그인정보 암호화·세션 서명·화면공유
  티켓을 전부 겸용**하는 구조라 그대로 가져오지 않는 게 좋다 — 신규 포털은 처음부터 "몰
  로그인정보 암호화 전용 키"를 별도로 두고 시작할 것을 권장한다.
- **다운로드 게이팅**: 결제 전 산출물 파일에 직접 접근 가능한 URL이 새어나가지 않게(추측 불가능한
  토큰 + 서버측 결제상태 확인) 설계해야 한다.
- **감사로그**: 언제 요청이 생성/승인/완료됐는지, 언제 결제됐는지, 언제 다운로드됐는지를 전부
  기록해야 한다 — 분쟁·정산·세무 문의 대응에 필요하다.
- **PTP↔포털 경계**: 위 2-2절의 (A) 완전분리형을 택한다면, 운영자가 두 시스템을 오갈 때 몰
  ID/PW를 손으로 복사해 옮기는 과정 자체가 유출 위험 지점이 된다 — 최소한 "포털에서 PTP로 값을
  안전하게 전달"하는 절차(예: 포털 관리자 화면에서만 복호화해 볼 수 있게 하고, 클립보드 복사 후
  일정 시간 뒤 자동 클리어 등)를 정해두는 편이 좋다.

## 5. 단계적 설계 로드맵

1. **MVP(수작업 중심)**: 포털은 "요청 접수 폼 + 약정 동의 + 요청 목록 조회"만 자동화하고, 검토·
   처리·산출물 등록·알림·결제 확인은 운영자가 수작업(이메일/문자 직접 발송, 계좌이체 후 수기 확인
   등)으로 처리. 목적은 "고객이 직접 요청을 남기고 진행상황을 확인할 수 있게" 하는 최소 기능만
   빠르게 검증하는 것.
2. **부분 자동화**: PG 결제 연동(결제 성공 콜백 → 다운로드 자동 활성화), 이메일/SMS 자동 발송,
   요청 상태머신 자동 전이(결제 완료 시 자동으로 "종료" 처리 등).
3. **알림 채널 확장 + 운영 고도화**: 카카오 알림톡 연동(템플릿 심사 완료 후), 견적 자동 계산,
   PTP-포털 반자동 연동((B) 방식 검토), 정산/세금계산서 자동 발행.
4. **완전 자동화(장기)**: 헤드리스 자동화가 가능한 몰에 한해 요청 접수 즉시 PTP가 자동으로
   스크래핑을 트리거하는 파이프라인(로그인필수 몰은 이 단계에서도 여전히 사람 개입 필요 — 0절
   참고).
