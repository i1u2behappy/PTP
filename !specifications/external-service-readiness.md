# 대외 서비스화(범용 솔루션) 준비 검토

개발 지시가 아니라 **검토 문서**입니다 — 여기 적힌 항목을 곧바로 구현하라는 뜻이 아니라, "일반적인
대외 서비스가 가능한 범용 솔루션"으로 PTP를 준비할 때 무엇을 얼마나 보강해야 하는지 미리 가늠해두기
위한 자료입니다(2026-08-30 검토). 실제 착수 시점의 코드 상태와는 달라질 수 있습니다.

## 0. 전제 — 지금 PTP는 "1인/소수가 자기 PC에서 직접 쓰는 도구"다

가장 먼저 짚어야 할 건 개별 기능의 완성도가 아니라 **애초에 설계 전제 자체가 다중 사용자·다중
환경을 가정하지 않는다**는 점이다. 아래 모든 항목은 이 전제 위에서 파생된다.

- Next.js 개발서버 + 워커 프로세스(`worker/index.ts`) + PostgreSQL(Docker) + 로컬 Ollama가 전부
  **같은 Windows PC 한 대**에서 돈다. `npm run dev`/`npm run worker`를 사람이 직접 실행하고,
  죽으면 사람이 직접 재시작한다(`!specifications/dev-server-autostart-on-logon.md` 정도가 유일한
  자동화).
- 인증은 "회사 내부 여러 직원이 로그인하는 시스템"까지는 되지만(아래 2절), "서로 다른 고객사가 서로의
  데이터를 못 보게 격리된 SaaS"는 아니다 — `sites`/`mall_products`/`product_master`가 전부 하나의
  공유 네임스페이스에 있다.
- **개발자모드(로그인 필수 몰) 자체가 "이 PC의 이 크롬 프로필"에 물리적으로 묶여 있다** — 이건
  기능 하나의 문제가 아니라 "여러 고객이 각자 다른 몰을 동시에 운영"이라는 시나리오 자체와 정면으로
  충돌하는 구조적 제약이라 별도 절(1절)로 다룬다.

## 1. 가장 근본적인 구조적 제약 — 개발자모드의 "한 대의 PC" 종속

`lib/scraper.ts`의 `openManualLoginWindow`/`focusManualLoginChrome`는 이 PC에 실제로 설치된 크롬을
`--profile-directory=Default`로 직접 `spawn`하고, 창을 못 찾으면 PowerShell로 OS 창 포커스를 조작한다
(`PTP_MANUAL_LOGIN_CHROME_PROFILE = 'Default'`— 코드에 하드코딩). 확장(`extension-poc/`)도
`chrome.debugger`로 "지금 이 화면에 떠 있는 실제 탭"을 조작하는 방식이라, 서버가 어디 있든 결국
**사람이 실제로 로그인해둔 브라우저 창이 물리적으로 존재해야** 동작한다.

로그인 필수(회원전용) 몰이 하나라도 있는 고객은 이 구조상 다음 중 하나가 강제된다.

- 고객이 자기 PC에 크롬 확장을 설치하고 자기 브라우저에서 직접 로그인해야 한다(지금 방식 그대로) →
  고객마다 별도 설치/안내가 필요하고, "서버에 로그인만 시켜두면 끝"이라는 SaaS적 기대와 어긋난다.
  또한 확장이 Chrome 웹스토어에 정식 배포돼 있지 않아(4절) 설치 자체가 매끄럽지 않다.
  - `chrome.debugger` API는 "사용자가 개발자모드 확장을 직접 설치해 실행한 경우"를 전제로 설계돼
    있어, 이 구조를 유지하는 한 이 제약은 원천적으로 못 없앤다(브라우저 보안 모델 자체의 한계).
- 또는 회사가 "고객 수만큼의 가상 데스크톱(각자 크롬 프로필 하나씩)"을 운영하며 로그인을 대신
  해준다 → 인건비/운영부담이 고객 수에 비례해 늘어나는 구조라 "범용 솔루션"의 스케일 목표와 안 맞는다.

**결론**: 이 부분은 "기능 보강"이 아니라 **제품 전략 결정이 먼저 필요한 지점**이다 — (a) 로그인
필수 몰 지원을 고객 자기-설치 확장 방식으로 명확히 포지셔닝하고 그 경험을 다듬을지, (b) 이 유형의
몰은 아예 지원 범위에서 빼고 헤드리스 자동화가 가능한 몰만 정식 지원할지, (c) 인건비를 감수하고
대행 운영 모델로 갈지 — 어느 쪽이든 이후 인프라/소스 설계가 달라지므로 가장 먼저 결정해야 한다.

## 2. 인프라

| 영역 | 현재 상태 | 보강 필요 수준 |
|---|---|---|
| 앱 배포 | `Dockerfile` 없음, 앱 컨테이너 없음. `docker-compose.yml`은 로컬 개발용 Postgres 컨테이너 하나뿐(계정도 devuser/devpass 하드코딩) | **높음** — 최소한 Next.js 앱 + 워커를 각각 컨테이너화하고, dev/staging/prod 환경 분리(env 파일 자체가 `.env.local` 하나뿐, `.env.example`도 없음)부터 필요 |
| 워커 프로세스 관리 | `npm run worker`를 사람이 `nohup`으로 띄우는 수준. 메모리 임계치 자동 재시작은 있으나 PM2/systemd 등 프로세스 매니저·헬스체크·자동 재기동 인프라는 없음 | **높음** — 최소 systemd/PM2, 이상적으로는 워커를 큐 기반 잡 러너(예: 여러 스크랩 작업을 병렬 워커 풀이 순서대로 소비)로 재구성 |
| DB | Postgres 단일 인스턴스, 백업/복제/PITR 전략 문서화된 것 없음 | **높음** — 정기 백업, 최소 1개 이상 replica, 장애 시 복구 절차(RTO/RPO 목표) 필요 |
| 시크릿 관리 | `CREDENTIALS_ENCRYPTION_KEY` 하나(AES-256-GCM)로 몰 로그인 비밀번호 암호화 + 세션 서명(HMAC) + 화면공유 티켓까지 전부 겸용, 로테이션/버전관리 없음, 평문 `.env.local` 파일 하나에 전부 보관 | **높음** — 키 하나 유출 시 저장된 모든 몰 로그인정보 복호화 + 모든 세션 위조가 동시에 가능한 구조. 최소 용도별 키 분리 + KMS/Vault급 시크릿 저장소 + 로테이션 절차 |
| 관측성(로깅/모니터링) | 구조화 로깅·에러추적(Sentry 등)·메트릭 전부 없음, `console.log`/`console.error`가 전부 | **높음** — 대외 서비스는 "장애를 고객이 먼저 알아채기 전에 감지"가 최소 요건. 에러 추적기 + 최소한의 알림(디스크/DB/워커 다운) 부터 |
| 네트워크/보안 | 리버스 프록시·TLS 종단·WAF·요청 제한(rate limit) 관련 설정 확인 안 됨(로컬 개발 전제) | **중간** — 실제 인터넷 노출 시 표준 웹 서비스 보안계층(TLS, WAF, rate limit, CORS 정책 재검토) 필요 |
| AI 비용/쿼터 관리 | Anthropic/Gemini/Ollama 호출에 사용량 추적·쿼터·비용 상한 로직 없음(이번 세션에도 Anthropic 크레딧이 그냥 소진돼 조용히 Gemini/Ollama로 새는 상태였음) | **중간** — 고객이 늘면 AI 호출량도 비례 증가 → 사용자별/일별 쿼터, 비용 대시보드, 상한 초과 시 처리 정책 필요 |
| 스케일 아웃 | 단일 프로세스·단일 머신 전제, 수평 확장 경로 없음 | **중간~높음**(목표 고객 규모에 따라 다름) — 몰 단위 락(`withSiteLock`)이 프로세스 내 메모리 기반이라, 워커를 여러 대로 늘리면 이 락부터 분산 락(Redis 등)으로 바꿔야 함 |

## 3. 솔루션 소스/아키텍처

| 영역 | 현재 상태 | 보강 필요 수준 |
|---|---|---|
| 인증/권한 | `lib/auth.ts`에 자체 HMAC 서명 세션 쿠키 + `scrypt` 비밀번호 해시 + `admin`/`user` 2단계 역할 — 자체 구현치고는 기본기는 갖춤 | **중간** — 다만 조직/테넌트 개념이 없어 "회사 내부 여러 직원" 이상으로는 못 감(아래 멀티테넌시 참고). SSO/2FA/비밀번호 정책 등은 미검토 |
| 멀티테넌시 | `sites`/`mall_products`/`product_master`가 전부 하나의 공유 네임스페이스. `supply_clients`(거래처)는 "이 상품을 누구에게 넘기는지"를 뜻하는 비즈니스 개념이지, 데이터 격리 단위(테넌트)가 아니다(`master_schema_fields` 자체가 "거래처 구분 없이 시스템 전체가 공유"하도록 의도적으로 설계됨) | **매우 높음** — 서로 다른 고객사가 자기 몰/자기 상품만 보게 하려면 스키마 전반에 테넌트 경계를 새로 그어야 한다. 지금 구조를 그대로 여러 고객에게 판다면 "한 회사가 전용으로 쓰는 인스턴스를 고객마다 따로 띄우는" 모델(멀티 인스턴스)이 멀티테넌트 SaaS보다 훨씬 적은 개발량으로 갈 수 있는 현실적 경로 |
| 브라우저 확장 배포 | Manifest V3, 수동 버전 관리(현재 1.47)만 있고 Chrome 웹스토어 등록/자동 업데이트 체계 없음 — `--load-extension`으로 매번 로컬 폴더를 직접 로드하는 개발 배포 방식 | **높음**(1절의 로그인필수 몰 지원을 유지한다면) — 정식 배포하려면 웹스토어 심사·개인정보처리방침·권한(특히 `<all_urls>`+`debugger`는 심사 난이도가 높은 편)에 대한 소명 준비 필요 |
| 외부 입력 검증 | AGENTS.md 방침대로 Zod 검증을 신규 라우트부터 점진 적용 중, 기존 라우트는 아직 `as {...}` 캐스팅이 섞여 있음 | **중간** — 외부(고객) 요청이 직접 닿는 표면이 넓어지기 전에 기존 라우트도 전수 전환 권장 |
| 스크래핑 자체의 법적/정책 리스크 | robots.txt 준수, 대상 몰 이용약관, 과도한 요청으로 인한 대상 서버 부하, 수집 데이터 내 개인정보(구매후기 작성자명 등) 처리 방침 등이 코드/문서 어디에도 명시돼 있지 않음 | **높음** — "여러 외부 고객이 여러 몰을 스크랩"하는 서비스로 확장할수록 법적 리스크가 커진다. 최소한 (a) 요청 빈도 상한/차단 시 백오프 정책의 대외 공개 기준, (b) 개인정보 필드 취급 방침, (c) 서비스 이용약관상 "고객이 스크랩 권한을 가진 몰만 등록한다"는 책임소재 명시가 필요 |
| 다국어/특정 시장 종속 | UI 문구, 에러 메시지, 카테고리/게시판 판별 정규식(`NON_CATEGORY_TEXT_RE` 등)이 전부 한국어·한국 쇼핑몰 플랫폼(고도몰/카페24/메이크샵) 전제로 짜여 있음 | **목표 시장에 따라 다름** — 국내 2차유통/셀러 대상이면 문제 없음. 해외 확장이나 비-한국몰 지원이 목표라면 이 휴리스틱 상당수를 재설계해야 함 |
| 테스트 | 순수 함수 단위/속성 테스트(fast-check)는 꾸준히 축적 중, GitHub Actions CI도 존재 — 다만 e2e는 "실제 DB/로그인 계정 없음"을 이유로 CI에서 항상 스킵됨 | **중간** — 회귀 방지 기반은 있는 편. 다만 다중 사용자 시나리오(동시 접속/동시 스크랩 등)에 대한 부하·동시성 테스트는 없음 |
| 공개 API/외부 연동 | 외부에서 프로그래밍 방식으로 붙을 수 있는 공개 API, 웹훅, API 키 발급/버전관리 체계 없음(전부 내부 화면 전용 라우트) | **낮음~중간**(제품 방향에 따라) — 고객이 자기 시스템과 연동하길 원하는 시장이면 필요, 화면(UI) 중심 서비스로만 간다면 우선순위 낮음 |

## 4. 운영/유지보수 전략

- **배포/릴리스 프로세스**: 지금은 로컬에서 코드를 고치고 dev 서버가 그대로 반영하는 구조 —
  스테이징 검증 → 프로덕션 배포 → 문제 시 롤백이라는 표준 릴리스 파이프라인이 없다. 앱뿐 아니라
  **크롬 확장의 버전 릴리스**(수동 버전 bump, 배포 채널)도 별도로 관리해야 한다 — 서버는 배포했는데
  확장은 옛날 버전인 고객이 섞이는 상황을 어떻게 다룰지(하위호환 기간, 강제 업데이트 안내) 미리
  정해둬야 한다.
- **장애 대응**: 온콜/알림 체계, 장애 등급별 대응 절차, 상태 페이지(status page) 같은 고객 커뮤니케이션
  채널이 없다. 대외 서비스는 "장애가 났을 때 무엇을, 누가, 어떤 순서로 확인하는지"가 문서화돼 있어야
  한다.
- **백업/복구 훈련**: 백업이 있다는 것과 "실제로 복구가 되는지 주기적으로 리허설한다"는 것은 다르다 —
  현재는 백업 전략 자체가 없으니 이 단계는 아직 멀었다.
- **문서 이원화**: `!specifications/`는 개발팀 내부용 의사결정 기록(한국어, 매우 상세)이라 훌륭한
  자산이지만, 고객에게 보여줄 이용안내·FAQ·API 문서·이용약관·개인정보처리방침은 별도로 준비해야
  한다(내부 스펙 문서를 그대로 대외 공개하면 안 됨 — 보안/구현 세부사항이 섞여 있음).
- **컴플라이언스**: 개인정보보호법(PIPA) 관점에서 "고객사의 고객(최종 구매자) 개인정보가 섞인 데이터를
  PTP가 대신 처리/보관"하는 구조가 되면 위탁처리 계약, 개인정보처리방침 게시, 안전조치 의무 등이
  발생한다. 해외 고객까지 받는다면 GDPR 등도 검토 대상.
- **과금/사용량 측정**: 유료 모델이라면 사용량(몰 개수/스크랩 건수/AI 호출량 등) 측정과 과금 연동이
  필요한데 지금은 이런 계측 자체가 없다.
- **고객 온보딩**: 지금은 관리자가 직접 Mall/거래처를 등록해주는 수동 온보딩 구조 — 셀프서비스
  가입/설정을 지원할지, 아니면 계속 "영업+수동 세팅" 모델로 갈지도 결정이 필요하다(1절의 개발자모드
  제약과도 맞물림 — 로그인 필수 몰이 있으면 완전 셀프서비스는 어차피 어렵다).

## 5. 단계적 접근 제안(우선순위 가늠용)

실제로 손댈 때는 "전부 다 한 번에"가 아니라 목표 고객 규모에 맞춰 단계를 나누는 편이 현실적이다.

1. **0단계 — 결정 먼저**: 1절의 로그인필수 몰 지원 방식(고객 자기설치 vs 대행 vs 미지원)과, 3절의
   멀티테넌시 방식(진짜 멀티테넌트 SaaS vs 고객사별 별도 인스턴스)을 먼저 정한다 — 이후 모든 인프라/
   소스 설계가 이 두 결정에 갈린다.
2. **1단계 — 소수 고객 파일럿이 가능한 최소 수준**: 컨테이너화(Dockerfile) + 워커 프로세스 매니저 +
   DB 백업 + 에러 추적기(Sentry 등) + 시크릿 분리 + 기존 라우트 Zod 전환 + 이용약관/개인정보처리방침
   초안. 확장은 여전히 수동 설치 안내로 가능(웹스토어 등록은 뒤로 미뤄도 됨).
3. **2단계 — 여러 고객을 실제로 받는 수준**: (멀티테넌트로 결정했다면) 스키마 테넌트 격리 + 분산 락
   전환, 크롬 확장 웹스토어 정식 배포, AI 비용/쿼터 관리, 상태 페이지/온콜 체계, 백업 복구 리허설.
4. **3단계 — 범용/대규모**: 수평 확장(큐 기반 워커 풀), 공개 API, 과금/사용량 측정, 컴플라이언스
   심화(GDPR 등 해외 대응), i18n(목표 시장 확장 시).
