# 카테고리 탐지가 몰에서 로그아웃시키는 문제 — 원인과 3층 방어

## 증상 (2026-09-13, 투비즈온 실사용 신고)

몰 작업 중 로그인이 계속 풀린다("또 로그아웃 됨"). 사용자 화면에는 투비즈온의
`tobizon.co.kr/mall/member/grade.php?popupmode=y`(회원등급 안내) 팝업 창이 떠 있었다 — 아무도 누르지
않은 팝업이다.

## 확정된 원인 — 몰별 문제가 아니라 "전수클릭"이라는 탐지 방식 자체의 구멍

`lib/scraper.ts`의 `discoverCategoryMenuByExhaustiveHeaderClick`(2026-09-12 도입, 비전 AI가 "전체
카테고리" 버튼을 못 맞히는 몰의 마지막 수단)은 **헤더 영역의 작은 요소를 전부 하나씩 실제로 클릭해보고**
가장 많은 카테고리가 나오는 걸 채택한다. 후보를 고르는 기준(`nthHeaderIconCandidate`)이 **위치와 크기
뿐**이었다 — 그 요소가 무엇으로 이어지는지(href/텍스트)는 전혀 보지 않았다.

국내 쇼핑몰은 로그인 상태에서 헤더 우측 유틸리티 영역에 로그아웃/마이페이지/장바구니/회원등급 링크를
둔다. 이건 이 코드베이스도 이미 전제하고 있는 관례다 — `detectLoggedInSignal`이 "페이지에 '로그아웃'
링크가 있으면 로그인된 것"으로 판정한다. 즉 **로그인된 상태에서 이 경로를 타는 모든 몰은 구조적으로
로그아웃이 클릭된다.** 투비즈온은 그 경로를 타게 된 첫 몰일 뿐이다.

### 증거

- 워커 로그(`.worker.log`)에서 투비즈온 몰구조분석 3회 연속 같은 패턴:
  `헤더 아이콘 전수클릭: 후보 1..39` → 곧바로
  `로그인 세션이 끊긴 것으로 보임(종료 시점 로그인됨=false, 카테고리 확장 중 로그인차단=false)`.
  뒤쪽 괄호가 핵심이다 — "로그인 벽에 막혀서"가 아니라 **실행 도중에 세션이 죽었다**는 뜻.
- 세션이 끊긴 뒤 이어진 허브 확장은 모든 카테고리가 "상품 5개"로 균일 — 로그아웃 화면을 긁고 있었다.
  즉 피해는 "로그인 풀림"만이 아니라 **그 이후 수집한 몰구조분석 결과 전체가 로그아웃 상태 기준**이다.
- 투비즈온 실물 HTML 확인: `<ul class="header-top-links">`의 `<li><a href="/mall/member/login.php">`
  자리가 로그인 상태에서는 로그아웃/회원등급으로 바뀐다. 그 마크업을 그대로 본뜬 페이지로 실측한 결과
  수정 전 후보는 7개였고(로그아웃 `li`+`a`, 장바구니 `li`+`a`, 회원등급 `li`+`a`, 진짜 카테고리 `a`),
  로그아웃은 `li`/`a` 두 겹이라 **두 번** 클릭된다. 사용자가 본 `grade.php` 팝업은 후보 5·6번을 클릭한
  결과물이다.
- DB 확인: 저장된 카테고리 32개에는 로그아웃/회원 URL이 없었다 — 즉 이번 건은 2026-09-06 오토카필처럼
  "카테고리로 잘못 저장된 URL을 방문"한 게 아니라 **클릭 경로**다. 기존 방어는 전부 "어떤 URL로 이동할지"
  를 걸렀기 때문에, URL을 보지 않고 요소를 누르는 새 경로에는 하나도 걸리지 않았다.

패턴이 분명하다 — **카테고리를 찾는 새 방법을 추가할 때마다 같은 사고가 다시 난다.** 개별 호출부를
하나씩 고치는 방식으로는 다음 경로에서 또 뚫린다.

## 설계 — 3층 방어 (전부 몰 무관)

몰별 URL/도메인을 하드코딩하지 않는다. 새 몰에서 같은 증상이 나도 코드 수정 없이 막히는 것이 목표다.

1. **후보 수집 단계에서 제외** (`nthHeaderIconCandidate`) — 요소 자신과 조상 `<a>`, 자식 `<a>`의
   href/onclick/텍스트를 보고 계정·주문 링크(`ACCOUNT_UNSAFE_URL_RE`, `LOGOUT_TEXT_RE`)면 후보에서 뺀다.
   "전체 카테고리" 트리거가 계정 링크일 리 없으니 잃는 것이 없고, 헛클릭이 줄어 전수클릭이 빨라진다.
   (`CATEGORY_VISION_UNSAFE_URL_RE` → `ACCOUNT_UNSAFE_URL_RE`로 이름을 바꾼 것도 이 때문 — 더 이상
   비전 경로 전용이 아니라 "무엇을 클릭/방문할지" 공통 판정이다.)
2. **비전 좌표 클릭에도 같은 판정** (`clickNearestClickableAtPoint`) — 좌표에 있는 것이 계정 링크면
   클릭하지 않고 그냥 실패로 돌린다(raw `mouse.click` 폴백도 타지 않는다). 비전 좌표는 같은 화면에서도
   호출마다 흔들리는데, 몰 헤더는 "전체 카테고리" 버튼과 계정 링크가 바로 옆에 붙어있는 자리다.
3. **모든 브라우저 컨텍스트에 심는 전역 그물** (`blockLogoutClicks` + `installCommonInitScripts`) —
   페이지 안에서 capture 단계로 클릭을 가로채, 로그아웃으로 이어지는 클릭이면 `preventDefault` +
   `stopImmediatePropagation`. **어느 코드 경로가 무엇을 누르든** 로그아웃만은 일어나지 않는다. 앞으로
   새 탐지 방법이 추가돼도 이 층은 자동으로 적용된다.
4. **(패턴을 벗어나는 몰 대비) 결과로 판정** — 전수클릭 루프가 후보를 하나 클릭할 때마다 시작
   페이지에서 `detectLoggedInSignal`을 다시 확인해, 로그인 상태가 true→false로 바뀌면 남은 후보를
   클릭하지 않고 즉시 중단하고 로그에 남긴다. 1~3은 "우리가 아는 모양의 로그아웃"만 막지만, 이 층은
   **form 제출식이든 전혀 다른 URL이든 실제로 세션이 끊기면 걸린다.**

### 왜 route() 가로채기를 쓰지 않았나

"로그아웃 요청 자체를 네트워크 단에서 막으면 되지 않나"는 이 프로젝트에서 이미 실측으로 폐기된
방식이다 — `MALL_PROFILE_CONCURRENCY` 주석 참고(요청마다 Node 왕복이 생겨 "샘플 상품 6건" 단계가
46~91초 → 183초). 3번 그물은 브라우저 안에서 끝나 요청당 비용이 0이다.

### 사람이 진짜 로그아웃하려는 경우

전역 그물이 사람의 클릭까지 막으면 "버튼이 죽은" 것처럼 보인다(로그인 창에서 계정을 바꾸려는 경우 등).
그래서 같은 요소를 0.6~5초 안에 한 번 더 누르면 통과시키고, 첫 클릭 때 "정말 로그아웃하려면 한 번 더
클릭하세요" 토스트를 띄운다. 자동화는 같은 요소를 그 간격으로 두 번 누르지 않는다(전수클릭은 후보마다
페이지를 새로 불러오고, 비전 클릭의 폴백은 100ms 안쪽).

## 교차모드 영향

- **일반모드(서버 Playwright)**: 위 1~4 전부 적용. 사고가 난 경로가 여기다. 로그인 창이 열려 있으면
  `withContext`가 그 창을 재사용하므로, 이 클릭들은 **화면에 보이는 그 크롬 창에서** 일어난다 —
  사용자가 팝업을 눈으로 본 이유.
- **개발자모드(크롬 확장)**: 전수클릭/비전클릭 경로가 아예 없어 이번 사고 벡터는 해당 없음. 다만 확장은
  저장된 카테고리 URL을 **사용자의 진짜 크롬**에서 방문하므로, 로그아웃 URL이 한 번이라도 카테고리로
  저장되면 피해가 더 크다. 서버 쪽에는 있던 "방문 직전 가드"가 확장에는 없었으므로,
  `resolveSite()`가 목록을 받아오는 한 지점에서 `LOGOUT_URL_RE`로 걸러낸다(하위구조 확인/정렬 감지가
  같은 목록을 쓰므로 소비자마다 거르면 또 빠진다). manifest 1.67 → 1.68.

## 다른 몰에서 같은 증상이 나오면

1. 대부분은 위 1~3에 자동으로 걸린다(패턴 기반, 몰 무관).
2. 그래도 세션이 끊기면 4번이 잡아 로그에 남긴다:
   `헤더 아이콘 전수클릭: 후보 N을 클릭한 뒤 로그인 세션이 끊긴 것으로 보임 — ... LOGOUT_URL_RE/
   LOGOUT_TEXT_RE 보완이 필요한지 확인할 것`. 이 줄이 보이면 그 몰의 로그아웃 링크 형태를 확인해
   `LOGOUT_URL_RE`/`LOGOUT_TEXT_RE`에 한 줄 추가하면 — **패턴이 공용이라 그 순간 모든 몰에 적용된다.**
3. 새 패턴을 추가할 때는 `tests/unit/scraper.test.ts`의 `LOGOUT_URL_RE` 케이스에 실제 URL을 같이
   넣는다(오탐 방지 케이스도 함께 — 진짜 카테고리를 막으면 카테고리가 통째로 사라진다).

## 검증

- `npx tsc --noEmit` / `npm run lint` / `npm run test:unit`(273 → 279개) 전부 통과.
- 실제 크롬으로 직접 확인(투비즈온 헤더 마크업을 그대로 본뜬 페이지 + 실제 `withContext` 경로):
  - 전역 그물: 로그아웃 클릭이 페이지 스크립트에 **도달조차 못 함**, 진짜 카테고리 링크는 정상 클릭,
    0.8초 뒤 재클릭은 통과, 안내 토스트 표시 — 4개 모두 기대대로.
  - 후보 필터: 같은 페이지에서 **수정 전 7개 → 수정 후 1개**(진짜 카테고리 링크만).
  - 확인된 부수 사실: `page.setContent`는 CDP상 새 문서 네비게이션이 아니라 init script가 실행되지
    않는다(첫 검증이 그래서 실패했다). 실제 스크래퍼는 전부 `goto`를 쓰므로 영향 없지만,
    `extractFromHtml`처럼 setContent를 쓰는 경로에는 이 그물이 안 걸린다는 점은 알고 있을 것(그 경로엔
    클릭 자체가 없다).
- **아직 확인 못 한 것**: 실제 투비즈온 몰구조분석을 처음부터 끝까지 돌려 세션이 살아남는지. 실행에
  10분 이상 걸려(카테고리 구조 확인 196초 + AI 리포트 303초) 이번 세션에서는 돌리지 않았다.
