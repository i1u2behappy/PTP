## 0. 이 작업의 출발점 — AS-IS/TO-BE의 재정의

마이그레이션2_Transform의 AS-IS/TO-BE를 "아무 엑셀 두 장"이 아니라 다음으로 명확히 정의한다(사용자 설명, 2026-10-05):

- **AS-IS** = PTP 자체 프로세스("스크래핑 → 스크랩 확정")의 산출물. 몰에서 긁어온 원본 데이터.
- **TO-BE** = "각 오픈마켓 등록 양식에 전부 대응 가능한 PTP 공용 상품마스터 기준 포맷". 특정 마켓 하나의 업로드 양식이 아니라, 이후 단계(엑셀 내보내기의 마켓별 시트 변환, 오픈마켓 API 연동 — 이번 세션에 쿠팡 어댑터로 이미 구현)가 **공통으로 가져다 쓸 수 있는 상위 스키마**다.

즉 "상품마스터 컬럼"을 정하는 일은 Transform 하나만의 문제가 아니라, **스크랩→확정→(상품마스터)→엑셀내보내기/오픈마켓API**로 이어지는 전체 파이프라인의 중심 스키마를 정하는 일이다. 그래서 이 컬럼 집합은 "PTP 자체 기준"에 더해 "업계에서 이미 검증된, 여러 마켓에 두루 통하는 컬럼 집합"을 참고해 정해야 한다 — 그 참고 대상이 샵링커/사방넷/플레이오토다(셋 다 PTP가 지금 하려는 것과 같은 일, 즉 "여러 몰/마켓에 상품을 공급하기 위한 공용 상품마스터"를 이미 운영 중인 솔루션).

## 1. 외부 솔루션 조사 결과 (요약 — 전체는 별도 참고 문서)

전체 조사 내용·출처·PTP 설계 시사점은 [[reference-oms-product-master-formats]]에 따로 정리했다(이
프로젝트의 기존 관례 — `marketplace-formats/`가 이미 `coupang.md`/`reference-domesin-productdb.md`를
담고 있어, 외부 레퍼런스는 거기 쌓고 PTP 자체 설계 문서는 그걸 인용하는 구조를 그대로 따랐다).

요약: 샵링커/사방넷/플레이오토 셋 다 "마스터 상품"을 PTP와 같은 목적(여러 마켓 공용 기준)으로 운영하며,
용어만 다를 뿐 **상품명 → 카테고리 → 옵션 → 이미지 → 상세설명 → 주요정보 → 검색어/검색필터 → 상품정보제공고시
→ 배송/반품정보 → 대량관리**라는 같은 10단계 구조로 수렴한다. PTP 현재 컬럼과 대조한 결과는 §2.

한계: 세 솔루션 모두 **정확한 컬럼명 전체 목록은 로그인 후 화면/샘플 엑셀에서만 확인 가능**해, 공개 문서로는 "카테고리 구조"까지만 신뢰도 높게 확인했다 — "어떤 카테고리가 빠져있는지"는 알 수 있지만 "정확히 어떤 이름으로 넣을지"는 샘플 확보 전까진 추정이다(§5의 열린 질문 2).

## 2. PTP 현재 상품마스터 vs 외부 10개 카테고리 대조

| 카테고리 | PTP 현재 상태 | 비고 |
|---|---|---|
| 상품명 | ✅ `name_final` | |
| 카테고리 | ✅ `master_category` | |
| 옵션 | ✅ `options`, `option_combinations`(2026-10-03 보강) | |
| 이미지 | ✅ `thumbnail_urls`, `detail_image_urls` | |
| 상세설명 | ✅ `description` | |
| 주요정보 | ✅ brand/manufacturer/origin/가격 3종/재고 2종/내부코드/판매관리코드 | |
| **검색어/검색필터** | ❌ 없음 | 마켓 노출 검색엔진용 — 상품마스터에 없으면 마켓 등록 시 매번 따로 입력해야 함 |
| **고시정보(법정)** | ⚠ 쿠팡 어댑터에만 "등록 시점 입력값"으로 존재, 상품마스터 자체엔 없음 | 카테고리마다 세트가 달라 "고정 컬럼"으로 두기 어려움 — §3에서 구조 제안 |
| **배송/반품 정보** | ⚠ 거래처×마켓 단위 설정(`marketplace_credentials.settings`)으로만 존재 | 보통 거래처 전체에 한 번만 설정하면 되는 값이라 상품마스터 컬럼이 아니라 지금 구조가 맞음 — 그대로 유지 권장 |
| 대량관리 | ✅ 엑셀 내보내기/스크랩 대상 직접지정 | |

**결론**: 상품마스터 "컬럼" 차원에서 진짜 빠진 건 **검색어/검색필터** 하나다. 고시정보·배송정보는 "상품마다 다른 값"이 아니라 "카테고리마다/거래처마다 공통인 값"이라 상품마스터 컬럼으로 추가하기보다 지금처럼 별도 구조(카테고리 메타·거래처 설정)로 두는 게 맞다 — 이 부분은 뒤 §5 "열린 질문"에서 사용자 확인을 구한다.

## 3. 새 메뉴 "상품마스터 컬럼 관리" 설계

### 3.1 위치와 역할

- Sidebar: "마이그레이션" 그룹 안, "기준마스터테이블 관리"(admin 전용) 바로 다음에 추가. 같은 admin 전용 게이트.
- 역할: **별도의 스키마를 새로 만드는 화면이 아니라, 기존 `master_schema_fields`(기준마스터테이블 관리가 쓰는 바로 그 테이블)에 넣을 컬럼을 고르는 "카탈로그/추천" 화면**이다. 데이터 저장소를 둘로 쪼개지 않는다 — 실제 저장은 항상 기준마스터테이블 관리와 같은 API(`/api/master/schema`)를 그대로 쓴다.
  - 이렇게 하는 이유: 두 메뉴가 각자 다른 테이블에 저장하면 "어디가 진짜 기준인지" 헷갈리는 문제가 생긴다(이 프로젝트가 과거 "카테고리 캐시 덮어쓰기"류 사고를 여러 번 겪은 것과 같은 클래스의 위험). 카탈로그는 읽기 전용 참고자료, 저장은 기존 테이블 하나로 통일한다.

### 3.2 화면 구성 (안)

```

"내 상품마스터에 어떤 컬럼이 더 필요한지, 이미 상품마스터 체계를 운영 중인 솔루션(샵링커/사방넷/
플레이오토)의 구성을 참고해 고를 수 있습니다. 추가하면 바로 기준마스터테이블에 반영됩니다."

[탭] 샵링커 | 사방넷 | 플레이오토 | (전체 비교)

```

- 각 항목은 "이미 기준마스터에 있는지"를 `master_schema_fields`와 대조해 표시 — 이미 있으면 체크 비활성화(중복 추가 방지).
- "추가"를 누르면 선택한 항목들을 `is_custom=true`로 `/api/master/schema`에 PUT — 기준마스터테이블 관리에 가면 그대로 보인다.
- 카탈로그 데이터 자체(샵링커/사방넷/플레이오토가 각각 어떤 항목을 갖는지)는 **DB 테이블이 아니라 코드 내 정적 목록**(`lib/master/externalCatalogs.ts` 같은 파일)으로 둔다 — 외부 서비스가 아니라 이 프로젝트가 조사해 고정해두는 참고자료라 서버 저장이 필요 없다(기존 `FIXED_FIELD_INFO` 패턴과 동일).

### 3.3 "검색어/검색필터" 컬럼 제안(가장 먼저 추가할 후보)

이번 분석에서 유일하게 확인된 진짜 공백이라, 설계에 바로 반영할 구체안:

| field_key(안) | 라벨 | 비고 |
|---|---|---|
| `search_tags` | 검색어(태그) | 쉼표 구분 문자열. 마켓 등록 시 "검색어" 필드로 그대로 전송 |
| `search_filter_values` | 검색필터 속성값 | 카테고리별 속성이 마켓마다 달라 JSON으로 저장(`{속성명: 값}`) — AI 생성 모드로 Transform에서 채우기 적합 |

## 4. 데이터 모델 영향

- **신규 테이블 없음.** `master_schema_fields`(기존) 그대로 재사용.
- `lib/master/externalCatalogs.ts`(신규, 정적 데이터): 샵링커/사방넷/플레이오토별 카테고리→항목 목록. `FIXED_FIELD_INFO`와 같은 "서버 의존성 없는 순수 데이터" 파일.
- 신규 API 불필요 — 조회는 정적 파일 import, 저장은 기존 `GET/PUT /api/master/schema` 재사용. 굳이 새로 만든다면 "이미 있는지 대조" 로직은 클라이언트에서 `/api/master/schema` GET 결과와 비교하면 되므로 그마저도 불필요.

## 5. 열린 질문 (구현 전 확인 필요)

1. **고시정보/배송정보를 상품마스터 컬럼으로도 넣을지**: §2 결론대로 "상품마다 다른 값이 아니니 지금 구조 유지"로 보는데, 맞는지 확인 필요. 만약 "상품마다 다른 고시값"(예: 식품의 소비기한처럼 카테고리는 같아도 상품마다 값이 다른 경우)이 실제로 필요하면 얘기가 달라져 설계를 다시 짜야 한다.
2. **카탈로그 항목 정확도**: 공개 문서 기준이라 "카테고리 구조"는 신뢰도가 높지만 "정확한 필드명/개수"는 추정이 섞여 있다. 세 솔루션 중 실제 체험판 계정이 있으면 화면 캡처로 검증해 카탈로그 데이터를 더 정확하게 채울 수 있다 — 필요하면 진행.
3. **"검색어/검색필터" 외에 더 찾아야 할 공백이 있는지**: 현재는 이 하나만 확인됐는데, 이 정도 범위로 충분한지 아니면 더 깊게(유료 가입 등으로) 파봐야 하는지.

이 세 가지에 답을 주시면 바로 구현(메뉴 추가 + 정적 카탈로그 작성)에 들어가겠습니다.

## 6. 카테고리 매핑 파이프라인 — 현황 분석 및 설계 (2026-10-05 추가)

사용자 요청(2026-10-05): "ptp의 카테고리 매핑 단계에서도, 각 오픈마켓들의 카테고리 기준이 있어 이 카테고리
기준에 맞추어, 스크래핑한 '카테고리' 컬럼 → 상품마스터 카테고리 → 각 오픈마켓 대응 카테고리로 매핑해야
하는 프로세스"를 §0~5와 같은 선상에서 분석/설계. §0의 "상품마스터는 여러 마켓에 공용으로 대응하는 상위
스키마"라는 원칙이 카테고리 컬럼에도 그대로 적용되는 사례라, 이 섹션은 §3의 "컬럼 하나"가 아니라
**카테고리라는 컬럼 하나가 실제로 어떻게 흘러가는지 파이프라인 전체**를 다룬다.

### 6.0 현재 구조 — 3단이 아니라 "2단 + 끊어진 연결"

실제 코드를 끝까지 추적한 결과(아래 모두 file:line 근거), 사용자가 가정한 "스크랩 카테고리 → 상품마스터
카테고리 → 오픈마켓 카테고리"의 앞 2단은 존재하지만, **마지막 단(실제 등록/내보내기에 쓰는 지점)에서 그
결과를 전혀 읽지 않는다** — 즉 지금 "카테고리 매핑" 화면에 공들여 입력한 값이 실제 산출물에 반영되지 않는
"고아 데이터" 상태다.

| 단계 | 어디서 | 실제 동작 |
|---|---|---|
| 1단: mall_category → master_category | `lib/master/migrate.ts:98-101,120` | 최초 마이그레이션 INSERT 시 `mall_category` 값을 `master_category`에 그대로 복사. 재마이그레이션 UPDATE 절(`:102-118`)엔 `master_category`가 빠져 있어 이후엔 보존됨. 그 뒤로 바뀌는 유일한 경로는 ② "✨ AI로 분류 정리" 제안을 사람이 "적용"하거나(`CategoryMappingPanel.tsx` → `PUT /api/master/field-values`로 일괄 rename), ③ 다른 화면에서 수동 일괄변경하는 것뿐 — AI가 자동으로 써넣는 경로는 없음. |
| 2단: master_category → 마켓별 값 | `CategoryMappingPanel.tsx:151-182`, `app/api/category-mappings/route.ts:12-30` | "내부 카테고리(행) × 마켓(열)" 그리드에서 셀에 자유 텍스트를 입력 → `category_channel_mappings(master_category, marketplace_code, channel_category_value)` UNIQUE 키로 upsert/delete. 이 테이블은 AI 분류 제안의 "이미 확정된 카테고리 사전"(existingCategories, `classify/route.ts:42`)으로 읽기 용도로는 쓰인다. |
| **3단: 실제 등록/엑셀 산출물** | 쿠팡 등록: `app/api/marketplace/[code]/register/route.ts:40,46`, `lib/marketplace/coupang.ts:254`. 엑셀 내보내기(7개 마켓 전체): `app/api/export/route.ts:25` | **둘 다 `category_channel_mappings`를 조회하는 코드가 단 한 줄도 없다.** 쿠팡 등록은 사람이 등록화면에서 매번 `categoryCode`를 자유 텍스트로 직접 입력(선택한 상품 묶음 전체에 동일 값 적용, 상품별도 마켓별 매핑 자동조회도 아님). 엑셀 내보내기는 마켓이 무엇이든 `r.master_category \|\| r.mall_category \|\| ''`를 그대로 "카테고리" 컬럼에 씀 — 즉 네이버든 11번가든 지마켓이든 PTP 내부 라벨이 그대로 나간다. |

**왜 이렇게 됐는지(설계 의도, 버그 아님)**: `lib/marketplace/types.ts:40-53`의 주석이 명시 — "`channel_category_value`가 실제 마켓이 요구하는 코드와 같다는 보장이 없어(자유 텍스트로 사람이 입력한 값이라 라벨일 수도, 코드일 수도 있음) 자동 해석하면 조용한 오매핑 위험이 있다"는 이 프로젝트의 반복 원칙([[marketplace-api-integration]])에 따라 **일부러** 연결을 안 한 상태다. 다만 그 결과 "카테고리 매핑" 화면이 참고용 메모 이상의 역할을 못 하고 있다는 게 이번에 새로 확인된 사실이다.

### 6.1 이게 실무에 미치는 영향

- 쿠팡 열에 "운동화 → 78877"을 입력해둬도 실제 등록 시점엔 다시 손으로 쳐야 한다 — 화면 입력이 등록 작업을 줄여주지 못함.
- 엑셀을 받는 사람(또는 받아서 다시 업로드하는 사람)이 "카테고리" 컬럼에서 PTP 내부 라벨만 보고, 실제 그 마켓 카테고리 트리에 맞는 값은 엑셀을 받은 뒤 매번 따로 채워야 함.

### 6.2 설계 옵션 (구현 전 — 택1 또는 조합, 사용자 확인 필요)

**Option A — 등록화면 prefill (최소 변경)**: `MarketplaceRegisterPanel`이 마켓+선택상품의 `master_category`로 `category_channel_mappings`를 조회해 `categoryCode` 입력란에 **기본값으로 미리 채우되 여전히 사람이 확인/수정 후 제출**. "자동 해석 금지" 원칙은 유지(최종 전송 전 사람 눈을 반드시 거침), 반복 타이핑만 줄인다.

**Option B — 엑셀 내보내기 연결**: `app/api/export/route.ts`는 이미 호출 시점에 `marketplace` 파라미터를 단일값으로 받는 구조라(`:7-8`), 25번째 줄의 `category: r.master_category || r.mall_category || ''`를 `category_channel_mappings WHERE marketplace_code=$marketplace`로 LEFT JOIN한 값으로 우선 대체하고, 없으면 기존처럼 `master_category` 폴백 — **구현 난이도가 낮다(이미 마켓이 분리돼 호출되고 있어 조인 키가 이미 손에 있음)**. 이번 조사로 새로 확인된, Option A보다 더 작고 확실한 변경.

**Option C — 값 자체의 신뢰도 검증**: `channel_category_value` 입력 시 쿠팡의 "카테고리 정보 조회"(`category-meta`)처럼 실제 마켓 API로 그 값이 유효한 카테고리 코드인지 즉시 검증 — 가장 큰 폭의 변경이라 쿠팡 외 마켓은 해당 조회 API 유무부터 조사해야 함(§6.3).

이 셋은 서로 배타적이지 않다 — B(엑셀)는 지금 바로 해도 되는 수준의 변경이고, A(등록 prefill)·C(값 검증)는 "자동 해석 금지" 원칙과의 균형을 사용자가 먼저 확인해줘야 진행 가능.

### 6.3 분석이 아직 안 끝난 부분 (추가 조사 필요)

1. **쿠팡 외 마켓의 카테고리 체계 미조사**: `marketplace_configs`엔 네이버/11번가/지마켓/옥션/샵링커/사방넷 7개가 시드돼 있지만(`lib/db.ts:809-818`), 이들의 카테고리가 숫자코드인지/트리 path인지/이름인지, 조회 API가 공개돼 있는지 전혀 조사하지 않았다 — Option C를 쿠팡 외로 넓히려면 필요.
2. **엑셀을 받는 쪽의 실제 운영 관행 미확인**: "지금 엑셀의 카테고리 컬럼이 PTP 내부 라벨 그대로 나가는 게 실무에서 문제였는지"(매번 수작업으로 고쳐왔는지, 혹은 애초에 그 컬럼을 안 쓰고 있었는지) — 코드로는 알 수 없고 사용자 확인이 필요한 부분.
3. **mall_category→master_category 1단계의 "다대일" 가시성**: 지금은 "AI로 분류 정리" 배너에서 일시적으로만 "여러 원문 → 기존 카테고리 재사용" 제안을 보여줄 뿐, 상시 조회 가능한 "이 master_category엔 원래 mall_category가 몇 개 뭉쳐 있는지" 화면은 없다. 필요한지는 열린 질문.

### 6.4 열린 질문 (§5에 추가)

4. **(핵심)** §6.2의 Option A/B/C 중 이번 설계/구현 범위에 포함할 것은? 가장 작고 확실한 B(엑셀 연결)부터 우선할지, 등록화면 A까지 포함할지.
5. 엑셀 카테고리 컬럼의 실제 운영 불편 여부(§6.3-2) — 우선순위 판단 근거.
6. 쿠팡 외 마켓 카테고리 체계 공개조사(§6.3-1)를 이번에 진행할지, 아니면 API 어댑터가 아직 쿠팡뿐이니 엑셀(Option B)만 우선하고 나머지는 추후로 미룰지.
7. mall_category↔master_category 다대일 관계를 보여주는 상시 화면이 필요한지(§6.3-3), 아니면 지금의 AI 분류 제안 흐름으로 충분한지.

## 7. 사용자 확인 결과 (2026-10-05, 질문 7개 전부 답변 완료)

각 질문엔 참고로 제시한 샵링커/사방넷/플레이오토 사례를 함께 적는다(사용자 요청, "질문 시 다른 솔루션들의 사용 사례도 같이 붙여달라").

1. **고시정보/배송정보 컬럼화** — **지금 구조 유지로 확정.** (참고: 샵링커는 이 둘을 "마스터 상품"이 아니라 별도 "쇼핑몰별상품정보관리" 화면의 override 코드값으로, 사방넷은 배송정보를 상품이 아닌 "출고상품"(물류 SKU) 단위로 분리 — 셋 다 상품마스터 고정 컬럼으로 안 둔다는 점에서 PTP 현재 방식과 방향이 같음.) → §2 결론 그대로, 구현 변경 없음.
2. **카탈로그 정확도 검증** — **체험판 가입해서 검증하기로 확정**, 단 가입은 **사용자가 직접 진행 후 공유**(사업자등록번호/휴대폰 인증 등 실제 사업자 정보가 필요할 수 있어 대리가입은 보류). → §3의 새 메뉴용 `lib/master/externalCatalogs.ts` 카탈로그 데이터는 **사용자가 가입 후 화면 캡처/샘플 엑셀을 공유해줄 때까지 보류**. 그 전까지는 §3.3의 확정 항목(search_tags/search_filter_values)만 먼저 반영 가능.
3. **검색어/검색필터 외 추가 공백 3종** — **①②③ 모두 분석/설계에 포함하기로 확정**(사용자가 멀티선택 — "충분" 옵션과 함께 선택돼 의도가 애매했으나, 세 항목을 구체적으로 짚었다는 신호를 우선해 포함 쪽으로 해석; 다르면 정정 요청받을 것):
   - ① 마켓별 override 값 분리(샵링커) — 상품마스터 공통값과 별개로 마켓마다 다르게 낼 상품명/가격 등을 저장하는 구조. **설계 미착수.**
   - ② 재고단위/노출단위 분리(사방넷) — "출고상품"(SKU/바코드/박스입수)과 "판매상품"(마켓 노출용 상품명/설명)을 분리. **설계 미착수.**
   - ③ 기본정보/부가정보 화면 분리(플레이오토) — Transform의 "컬럼별 생성 규칙" 표가 전부 한 화면이라 TO-BE 컬럼이 많아지면(현재 실사용 90개) 다루기 번거로움. **설계 미착수.**
   - 세 가지 모두 §3(신규 메뉴)보다 범위가 커서(스키마+UI 구조 변경) 별도 설계 라운드가 필요 — 다음 세션에서 이어서 분석.
4. **카테고리 연결 범위** — **Option B(엑셀 연결)만 우선 확정, 구현 완료.** (참고: 샵링커 가이드북도 "카테고리는 내부 분류, 마켓별 트리엔 나중에 매핑"이라 명시해 PTP와 같은 2단 구조를 씀 — 다만 등록 시점 완전자동 여부는 공개자료로 미확인.) `app/api/export/route.ts`에서 `marketplace_code`로 `category_channel_mappings`를 조회해 매핑값이 있으면 우선 사용, 없으면 `master_category` → `mall_category` 순 폴백(코드: `categoryMap` 조회 + 폴백 체인). Option A(등록화면 prefill)/C(값 검증)는 **보류**(쿠팡 외 마켓 카테고리 체계 조사가 전제라 §6.3-1 공개조사도 함께 보류).
5. **엑셀 카테고리 컬럼 실무 불편 여부** — **"불편했음, 체감 문제 있었음"으로 확인** → 4번의 Option B를 "나중에 해도 되는 개선"이 아니라 "이미 체감된 문제의 수정"으로 재분류, 우선 구현 완료(위 4번).
6. (쿠팡 외 마켓 카테고리 체계 공개조사) — 4번 답변(B만 우선)으로 **사실상 불필요해져 질문에서 제외**.
7. **mall_category↔master_category 다대일 상시화면** — **지금 흐름(AI 분류 제안 배너)으로 충분, 신규 화면 불필요로 확정.** (참고 사례 없음 — 3개 외부 솔루션 공개문서가 이 부분을 직접 다루지 않는, PTP 자체 운영 이슈라고 사용자에게 명시했음.)

## 8. 심층 공개자료 조사 (2026-10-05, §7-2 보강 — 체험판 가입 불필요였음)

사용자 요청("각 서비스 홈페이지의 교육자료나 메뉴얼, 동영상 자료, 제품 소개자료 등을 더 분석해서 필요한 정보를 더 얻어봐")으로 샵링커/사방넷/플레이오토 세 서비스의 공개 가이드북·매뉴얼·도움말·제품소개를 에이전트 3개로 병렬 심층조사했다(로그인 없이 공개된 자료만 사용, 회원가입 폼엔 어떤 개인정보도 입력하지 않음 — 지시사항으로 명시). 전체 조사 내용·출처는 [[reference-oms-product-master-formats]]에 반영했고, 여기선 이 설계 문서에 영향을 주는 부분만 정리한다.

- **§7-2 정정**: "체험판 가입이 필요하다"고 판단했던 것과 달리, 세 솔루션 모두 로그인 없이 공개된 공식 문서만으로 §2/§3.3 수준을 훨씬 넘는 정밀도를 확보했다 — 샵링커는 Notion 기반 공개 가이드북(`guide.shoplinker.co.kr`, 실제 입력화면 스크린샷 포함), 사방넷은 공식 사용설명서 포털(`docs.sabangnet.co.kr:1975/sabangnet`, 용어사전 전체 공개), 플레이오토는 `plto.com` 고객센터 도움말 수십 페이지. **체험판 가입은 더 이상 §3 구현의 선행조건이 아니다.**
- **사방넷 분류 정정**: 이전에 "풀필먼트형"으로 따로 분류했던 `sbfulfillment.co.kr`은 별도 제품이 아니라 `sabangnet.co.kr`(메인, ㈜다우기술)의 창고관리(WMS) 서브모듈임을 양쪽 사이트 사업자등록번호 대조로 확인했다.
- **§7-3 세 가지 추가 공백을 뒷받침하는 교차검증**(자세한 근거는 참고 문서의 "교차 검증" 절):
  1. **마켓별 override(§7-3①)** — 세 솔루션 모두 독립적으로 확인됨: 샵링커 가격 7종(자체3+몰별3+시작가), 카테고리 3단(그룹 기본값 + 4단 드롭다운 + 등록시점 "샵링커/거래처/수동" 택일), "키워드(상품약어)"가 사실상 특정몰(인터파크 계열) 전용; 사방넷 고시정보 "쇼핑몰별 적용 가능"; 플레이오토 EMP "품목정보2~5"(몰마다 다른 고시값 최대 5세트). **특히 고시정보의 "최대 5슬롯" 설계가 샵링커("인증정보1~5")와 플레이오토(EMP "품목정보2~5")에서 서로 독립적으로 수렴**했다 — PTP가 §2에서 "고시정보는 상품마스터 컬럼이 아니다"라고 내린 결론 자체는 유지되지만(여전히 "상품마다 다른 값"은 아님), **"몰마다 다른 고시 템플릿·검색어·가격을 담을 override 그릇"이 PTP엔 아직 없다**는 게 이번에 새로 뚜렷해진 간극이다.
  2. **재고/노출 단위 분리(§7-3②)** — 사방넷이 메인 서비스 레벨에서 "사방넷상품(마스터)↔SKU/단품(물류)↔쇼핑몰상품(채널)" 3단 구조로, 플레이오토가 EMP "세트" 개념으로 각각 확인 — 1개 솔루션만의 특이사례가 아니라는 근거가 보강됐다.
  3. **화면 분리(§7-3③)** — 플레이오토의 "기본상품양식/옵션전용/품목정보전용(고시)/카테고리전용/단일상품/ESM" 6종 분리형 엑셀 양식으로 재확인.
- **카테고리 매핑 모델(§6)은 수정 불필요**: 사방넷("카테고리매핑", 사전 매핑 테이블)과 플레이오토("카테고리 템플릿 관리", 사전 매핑)가 PTP의 `category_channel_mappings`와 같은 "사전 매핑형"이라 다수(2/3)가 일치한다. 샵링커만 "등록 시점에 표준/거래처값 중 택일"하는 더 동적인 모델이라 다르지만, 이미 구현 완료한 §6 Option B(엑셀 연결)의 전제를 바꿀 사안은 아니다 — 참고로만 기록.
- **보안 메모**: 샵링커 가이드북 사이트(`guide.shoplinker.co.kr`)에서 클릭 후 경쟁사(사방넷) 사이트로 무작위 리다이렉트되는 현상이 조사 중 반복 관측됐다(추적/광고 스크립트 의심, 로그인 정보는 입력하지 않음) — 재방문 시 참고.

### 갱신된 다음 단계

- **바로 가능**: §3.3의 `search_tags`/`search_filter_values` 두 필드는 이미 설계 확정 상태라, 기존 "기준마스터테이블 관리" 화면에서 바로 커스텀 필드로 추가 가능(새 메뉴 완성과 무관하게 독립적으로 진행 가능) — 필요시 바로 요청.

## 9. 메뉴 수준 재점검 결과 (2026-10-05, 사용자 요청 — "전체적으로 프로세스를 재점검해봐")

사용자가 명확히 한 의도: 세 솔루션을 분석한 목적은 "상품마스터 컬럼 몇 개 채우기"가 아니라, **PTP도 결국
각 오픈마켓에 상품을 등록·관리하는 같은 목적의 도구이니, 각 솔루션의 메뉴 전체에서 장점을 파악해 PTP에
들여올 기능을 판단하는 것**이었다. 이 기준으로 전체 메뉴를 다시 대조한 결과는
[[marketplace-formats/reference-oms-product-master-formats]]의 "PTP 참고용 — 메뉴 수준 전체 지도" 절에
정리했다. 이 섹션엔 그 중 이 설계 문서에 직접 영향을 주는 결론만 요약한다.

- **§7-3①(마켓별 override)은 [[marketplace-channel-overrides]]로 분리 설계 완료** — 위 §8 "갱신된 다음 단계" 참고.
- **신규 발견 — 계층형 카테고리 부재**: 세 솔루션 모두 카테고리를 "대/중/소" 등 계층 드롭다운으로 다루는데, PTP의 `master_category`는 계층이 없는 평문 텍스트 하나다. 지금 당장 문제를 일으키진 않지만(AI 분류 제안도 문자열 일치로 동작), 카테고리가 많아지면 평문 하나로는 "의류 > 남성의류 > 상의" 같은 관계를 못 나타낸다 — 별도 설계 필요 여부는 다음에 판단.
- **신규 발견 — 복수 판매계정 불가**: `marketplace_credentials`가 `UNIQUE(client_id, marketplace_code)`라 거래처당 마켓당 계정이 1개뿐이다. 샵링커·플레이오토는 이를 지원한다. [[marketplace-channel-overrides]] §2에 분리해뒀다 — override 설계와는 다른 종류의 변경(인증 관리 스키마 자체를 건드림)이라 실제 수요 확인이 먼저 필요.
- **스코프 경계 확인**: 세 솔루션은 주문/CS/정산/통계/창고관리(WMS)까지 포괄하는 풀 OMS지만, PTP의 미션("수집→마스터화→등록")과 맞지 않아 참고 대상에서 의도적으로 제외했다 — 나중에 PTP가 그 영역까지 넓히면 참고 문서의 "스코프 경계" 절에서 이어서 조사하면 된다.
- **PTP가 오히려 앞선 부분도 확인됨**: 오픈마켓 API 직접등록(쿠팡 어댑터)과 AI 보조 기능(카테고리 분류/Transform 자동채우기 등)은 세 솔루션 공개문서 기준으로 PTP가 비슷하거나 더 앞서 있을 가능성이 있다 — 전부를 따라갈 필요는 없다는 뜻이기도 하다.
