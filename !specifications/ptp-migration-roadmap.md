## 00 · 한눈에 보는 요약

세 갈래로 나눠 조사했다 — ① PTP 코드베이스가 2·3단계를 실제로 어디까지 구현해뒀는지, ② 같은 문제
(이종 소스 데이터 → 표준 스키마 변환, 증분 동기화)를 이미 풀어둔 외부 사례, ③ 4단계로 요청받은
오픈마켓 API 연동의 현황과 레퍼런스.

- **2·3단계는 생각보다 훨씬 완성돼 있다.** 사이드바 메뉴 11개 전부 실제로 동작한다. 그중
  "마이그레이션2_Transform"은 이미 AS-IS/TO-BE 엑셀 쌍으로 AI가 컬럼 변환 규칙을 학습하는, "방법(b)"의
  초기 구현체다.
- **업계는 (a)+(b)를 나누지 않는다.** 상용 임베디드 임포터와 2024~2026 LLM 스키마매칭 연구 모두
  "AI가 매핑을 제안 → 사람이 수동매핑 화면에서 확정"하는 단일 파이프라인으로 수렴한다.
- **4단계는 설계만 있고 구현은 0.** 마켓 테이블·인터페이스는 이미 있지만(`lib/marketplace/types.ts`)
  실제 어댑터·인증정보 저장소·동기화 상태 추적은 전부 비어있다. 코드 주석은 이 기능을 이미 "5단계"로
  부르고 있어 번호 확인이 필요하다.
- **가장 위험한 실패모드는 "조용한 오매핑".** Amazon 사례의 경고이자, 이 프로젝트가 AGENTS.md에
  이미 기록해둔 과거 사고 패턴과 정확히 같다. 설계 전체에서 가장 우선해야 할 안전장치다.

## 01 · 현황 — 2·3단계 (마이그레이션 · 연속관리)

### 전체 데이터 흐름

중요한 사실 하나: "마이그레이션"은 스크랩 검토 후의 별도 단계가 아니라, **"확정(병합)" 버튼을 누르는
순간 1차 정규화와 최종 표준화가 한 번에 실행**된다.

```
스크랩 세션(scrape_staging_items)
  → [확정(병합) 클릭] → mergeStagingItems
      → mall_products(몰별 1차 정규화)
      → 같은 클릭 안에서 즉시 migrateToMaster(규칙 기반, AI 없음) 호출
          → product_master(status=draft)
              → 보강 메뉴 9종(판매관리코드·카테고리매핑·관리코드·상품명·옵션·브랜드/원산지·이미지·가격·기준스키마)
                  → 사람이 status=ready 확정 → 엑셀 내보내기(마켓별 양식)

마이그레이션2_Transform: mall_products ← AS-IS/TO-BE 엑셀 쌍 업로드 → 컬럼별 AI 변환 + few-shot
  → draft 검토 후 product_master에 반영

마이그레이션3_연속관리: product_master → 변동 감지
  → 재마이그레이션(migrateToMaster로) / 재수집(mall_products로, 선택 재방문)
```

실선 = 항상 자동 실행되는 경로. 점선(Transform/연속관리) = 사용자가 선택적으로 돌리는 보조 경로.

### 메뉴별 구현 상태

| 메뉴 | 상태 | 실제 내용 |
|---|---|---|
| 판매관리코드 관리 | 동작함 | 몰×거래처별 변환 "레시피"(값변경·조합·AI 스텝 순차 실행) 저장/미리보기 |
| 카테고리 매핑 | 동작함 · 순수 수동(당시) | 내부 카테고리 × 마켓 그리드에 셀 단위 수동 입력. 당시엔 AI 분류 없음 — `master_category`는 몰 원문 그대로 복사 |
| 관리코드 생성 | 동작함 | 거래처 코드 접두어 + 순번 자동 발급, 마이그 시 자동 실행 가능 |
| 상품명 관리 | 동작함 · AI 사용 | 대표이미지+원본명을 비전 모델에 넣어 생성. 템플릿 선택 가능 |
| 옵션 관리 | 동작함 · 순수 수동(당시) | "옵션명: 값1,값2" 텍스트 파싱만, 당시엔 AI 없음 |
| 브랜드·제조사·원산지 관리 | 동작함 · 순수 수동(당시) | 값 수정 시 동일값 쓰는 전체 상품 일괄 반영, 당시엔 AI 없음 |
| 이미지 편집 | 동작함 | 대표/상세 이동, 선택삭제. AI 없음 |
| 이미지 호스팅 관리 | 동작함 · 최소기능 | base_url 단일설정 — 의도적으로 이게 전부 |
| 가격 및 이익 관리 | 동작함 · 순수 수동(당시) | 셀 편집 + 예상마진 계산, 당시엔 AI 없음 |
| 기준 마스터테이블 관리 | 동작함 · admin 전용 | 거래처 구분 없는 전역 단일 스키마(과거엔 거래처별이었다가 단순화됨) |
| **마이그레이션2_Transform** | 동작함 · AI 사용 · 완성도 최상 | AS-IS/TO-BE 엑셀 쌍 업로드 → 컬럼별 ai/lookup/copy/composite 규칙 → few-shot 기반 생성 → draft 검토 → 반영 |
| **마이그레이션3_연속관리** | 동작함 · 뼈대 완성 | 변동감지·재마이그레이션·재수집·몰구조체크 4종. AI 고도화는 범위 밖으로 의도적으로 남겨둠 |
| 엑셀 내보내기 | 동작함 | `status=ready`인 것만 대상, 마켓별 양식 다수 구현 |

### AI 사용 지점 vs 순수 규칙 지점

조사 시점(2026-10-01) 기준 AI가 실제로 쓰이는 곳은 **정확히 두 곳**뿐이었다 — 상품명 생성, Transform의
ai 규칙 컬럼. 나머지(카테고리 매핑, 옵션, 브랜드/원산지, 가격)는 전부 사람이 그리드에서 직접 고치는
수동 도구였다. 게다가 이 두 AI 지점은 스크랩 단계의 AI 함수들과 달리 **멀티공급자 장애대응
(Anthropic→Gemini→Groq→Ollama) 체인 밖에 있었다** — Anthropic 장애 시 조용히 빈 값/축약명으로
폴백했다(이후 `7ef4feb`로 해결).

#### 발견된 약한 고리 (조사 시점 기준)

| 지점 | 문제 | 심각도 |
|---|---|---|
| `reference_products` 폴백 | 읽기 코드만 있고 INSERT하는 코드가 전무 — "이전 완료 데이터로 빈 칸 채우기"가 영원히 안 채워지는 죽은 경로 | 죽은 코드 (→ `41c549c`로 해결) |
| `master_category` | AI 분류 없이 몰 원문 그대로 복사 — "카테고리 매핑"은 표준화가 아니라 "원본값→마켓값" 수동 매핑 | 기능 공백 (→ `ca58cf8`로 해결) |
| 마이그레이션 AI 2곳 | 멀티공급자 폴백 미적용, Anthropic 단독 의존 | 리스크 (→ `7ef4feb`로 해결) |
| 가격 변동 자동반영 | 연속관리에서 가격 변경은 "참고용 표시"만, 자동 반영 안 됨(의도된 설계지만 재논의 여지) | 정책 결정 필요(열린 질문 1, 미해결) |

#### 3단계가 재활용할 수 있는 기존 빌딩블록

- **COALESCE 기반 멱등 upsert**(`migrateToMaster`) — 기계값은 갱신, 사람이 입력한 값은 보호. 재마이그레이션용
  새 merge 로직이 필요 없는 핵심 재사용 자산.
- **`is_already_migrated` 플래그** — 재스크랩 시 이미 가공된 상품은 덮어쓰지 않고 터치만 — "변경분만
  반영" 요구사항에 이미 맞는 메커니즘.
- **`stock_snapshots`** — 변경 시점마다 쌓이는 이력, 가격/재고 타임라인으로 바로 확장 가능.
- **`/api/master/changes` diff 로직** — `mall_products` vs `product_master` 필드별 비교가 이미 구현,
  확장하기 쉬운 구조.
- **Transform의 draft→commit 엔진** — 연속관리가 이미 그대로 재사용 중(재마이그레이션이 같은 엔진
  호출). "컬럼 변환 규칙"과 "변경분 재반영"이 이미 하나의 엔진으로 통합돼 있음.

## 02 · 현황 — 4단계 (오픈마켓 API 연동)

> **용어 확인**: "거래처 관리"는 오픈마켓과 무관하다 — `supply_clients` 테이블은 사업자등록번호·대표자명·
> 지급계좌가 들어가는 **B2B 납품 상대(도매 거래처) 정보**다. 오픈마켓은 완전히 별개 축인
> `marketplace_configs`/`marketplace_code`로 다뤄진다.
>
> **번호 체계 확인 필요**: `lib/marketplace/types.ts`의 주석은 이 기능을 이미 **"5단계"**로 부르고
> 있다. 요청받은 "4단계"와 다르다 — 단순 호칭 차이인지 확인이 필요하다(열린 질문 3).

| **쿠팡**(Wing Open API) | 3종 모두 제공. 수정은 부분 PATCH가 아니라 전체 JSON을 다시 보내는 방식 | `displayCategoryCode` 기준 메타데이터 조회 API로 옵션·고시정보·필수서류를 동적으로 받아야 함(카테고리마다 완전히 다름) | 임시저장→승인요청→승인완료(영업일 2~3일, 식품/화장품은 더 걸림). 2026-07-10부터 벤더ID당 초당 5회 rate limit. 가격/택배사 등 일부는 API로 불가 |
| **네이버 스마트스토어**(커머스API v2) | 등록/수정/삭제 모두 제공(v1 폐지, v2 이관). 재고/가격만 가볍게 바꾸는 경량 API 별도 제공(2025-01 출시) | `leafCategoryId` 필수. 단 "상품정보제공고시" 조회는 대분류 ID 기준이라 레벨이 섞여 실수하기 쉬움 | API별 개별 rate limit, 초과 시 "Burst Max"로 일시적 2배 허용(연속 불가) |
| **ESM PLUS**(지마켓·옥션 통합) | REST 방식 등록/수정/조회 확인. "마스터 상품번호" 하나로 등록하면 사이트별 상품번호 자동 생성 | 확인 안 됨 | ESM+ 마스터 ID 생성(지마켓·옥션 판매회원)이 선행 조건. rate limit/승인절차 확인 안 됨 |
| **11번가**(Open API) | 확인 안 됨 — 포털 존재는 확인, 엔드포인트는 로그인 후 열람 필요 | 확인 안 됨 | 확인 안 됨 |

공통점 하나는 분명하다 — **네 마켓 모두 "카테고리마다 요구 속성이 동적으로 달라 메타데이터를 API로
조회해 맞춰야 한다"**는 패턴. PTP가 쿠팡 한정으로 이미 발견해둔 "슬롯 라벨이 카테고리별로 다르다"는
문제의식과 정확히 일치한다.

## 03 · 외부 레퍼런스

세 영역 — ① 이종 소스→표준 스키마 매핑, ② 증분 동기화, ③ 멀티채널 오픈마켓 연동 — 전부 이미
안정화된 참고 사례가 있다.

### 스키마 매핑 — PIM · 임베디드 임포터

- **Pimcore 생태계 — SDM Portal**([sdmportal.com](https://sdmportal.com/)): 공급사 파일 컬럼을 1회
  드래그로 매핑하면, 이후 같은 구조의 파일은 **모델 재호출 없이 고정 규칙만 재생(replay)**하는 결정론적
  방식으로 처리. 구조가 바뀌면 해당 프로파일이 자동으로 "검토 대기"로 전환. → (a)+(b)+(c) 요구사항이
  가장 정확히 겹치는 사례 — 1회 매핑 → 무인 반복 → 구조변경 자동감지 → 변경분만 upsert.
- **Flatfile / Dromo / OneSchema**([flatfile.com](https://flatfile.com/product/mapping/)): 셋 다
  "개발자가 타겟 스키마를 사전 고정 → 사용자가 임의 구조 업로드 → AI가 컬럼 매핑 제안 → 사람이 틀린
  것만 드래그로 수정"하는 동일 패턴. **"완성 예시 파일에서 스키마 자체를 역추론"하는 기능은 셋 다
  확인 안 됨.** → 업계 표준은 "타겟 고정 + 소스 자동매핑" — "완성본에서 스키마 역추론"은 업계 레퍼런스가
  희박한 차별화 영역.
- **키픽AI(국내)**([kipic-ai.com](https://www.kipic-ai.com/)): 도매몰에서 받은 "서식 없는" 엑셀을
  올리면 AI가 상품명/키워드 생성 → 카테고리별 스키마에 속성 자동 매핑(필수 누락 필드 식별 포함) →
  이미지 가공까지. 건당 과금, 1회 최대 1000개 배치. 아래 심층 분석 참고.
- **Salsify — Universal Properties**([salsify.com](https://www.salsify.com/)): 리테일러별로 매번
  매핑하는 대신, 내부에 "표준 중간 스키마"를 한 번 정의해두고 여러 타겟 신택스로 변환 규칙만 N개
  유지하는 허브앤스포크 구조. → 소스(여러 도매몰)뿐 아니라 타겟(여러 판매채널)도 N개인 이 프로젝트에
  구조적으로 들어맞는 원칙.

#### 키픽AI 심층 분석 — 구조와 PTP 적용점

홈페이지 전문을 직접 확인했다. "각 작업단계를 일반 사용자가 직접 수행할 수 있는 구조로 만들어 뒀다"는
가설은 정확하다. 다만 범용 스키마매핑 엔진이 아니라 **좁게 정의된 3개 모듈 + 크레딧제**로 구현돼 있다는
점이 PTP와의 핵심 차이다.

| 구성 | 내용 |
|---|---|
| 전체 흐름 | ① 상품 대장(엑셀) 업로드 → ② 모듈별 "가공하러 가기"로 AI 실행 → ③ 엑셀 다운로드 후 마켓 업로드. 일괄 처리와 개별 모듈 선택 둘 다 지원 |
| 3개 독립 모듈 | 키워드 자동화(상품명·키워드·태그) · 속성 자동화(네이버 카테고리 속성 매핑) · 이미지 생성(대표/연출컷) — 각각 별도 버튼으로 독립 실행 |
| 검수 장치 | 상품명·키워드는 "사람이 수정할 포인트까지 함께" 표시, 속성은 "금지값·중복·누락 필수값 자동 검증", 이미지는 상품당 3회까지 무료 재가공 |
| 크레딧 | 텍스트 계열(상품명·키워드·속성·마이카테) 1크레딧/건, 이미지 2크레딧/건 — 구독료 없이 선불 크레딧 차감, 미사용분 이월 |
| 입력 요구사항 | "양식 맞출 필요 없음" — 단, 상품명/키워드/이미지 URL 최대 3개라는 한정된 필드만 휴리스틱으로 자동 인식 |
| 배치 한도 | 1회/1일 최대 1,000개 — 네이버 API 호출 한도가 원인이라고 명시 |
| 유틸리티 도구 | 테마 상품 추출기(VLOOKUP 대체)·마이카테 매칭·카테고리 분류기·엑셀 분할/병합 — 메인 AI 파이프라인과 분리된 보조 도구, 등록 전후 엑셀 잡무 처리용 |

**PTP 적용 체크리스트**
1. 나머지 수동 메뉴에도 같은 패턴을 복제한다 — 상품명 관리의 "독립 AI 버튼 + 사람 확정" 패턴을
   카테고리 매핑·옵션·브랜드/제조사/원산지·가격에도 복제. **(2026-10-03 완료 — 진행 현황 표 참고)**
2. "수정 포인트 하이라이트" 검수 UX를 추가한다 — 확신도가 낮은 필드를 시각적으로 구분. **(미착수)**
3. 무료 재가공 횟수 cap을 상품명·Transform AI에도 둔다. **(미착수)**
4. 제출 전 검증 패스를 카테고리 매핑과 4단계 오픈마켓 연동에 공유한다. **(미착수, 4단계와 함께)**
5. 대량 작업 전 "일일/배치 한도" 안내를 명시적으로 띄운다. **(2026-10-03 완료, `de08a6f`)**

> **그대로 베끼면 안 되는 지점**: 키픽AI의 "양식 맞출 필요 없이 자동 인식"은 범용 스키마 매핑이 아니라
> 상품명·키워드·이미지 URL 3개라는 한정된 필드에 대한 휴리스틱이고, 속성 매핑도 네이버 스마트스토어
> 단일 마켓 기준이다. PTP의 기준 마스터스키마는 필드 수가 훨씬 많고 타겟도 여러 몰/여러 마켓이라,
> "매핑 확인 없이 자동 인식"을 전체 필드로 일반화하면 "타겟 스키마 사전 고정 + 소스 자동매핑, 역추론은
> 별도" 원칙을 깨게 된다.

### AI/LLM 기반 스키마 매칭 — 2024~2026 연구

- **Schema Matching with LLMs (VLDB 2024)**([arXiv:2407.11852](https://arxiv.org/abs/2407.11852)):
  프롬프트 컨텍스트가 너무 적어도 많아도 매칭 품질이 떨어진다. 결론은 "LLM은 전체 자동화보다 초기
  매핑을 부트스트래핑하는 보조 도구로 유용". → 완전자동이 아니라 "제안 + 사람 확정" 구조를 학술적으로도
  뒷받침.
- **ReMatch — 검색증강 스키마 매칭**([arXiv:2403.01567](https://arxiv.org/abs/2403.01567)): 임베딩
  후보 검색(효율성) + LLM 의미이해(정확도) 결합 3단계 파이프라인. 스키마 메타데이터만으로 동작, 소스
  DB의 실제 데이터 접근 불필요. → 외부 도매몰 데이터를 다루는 이 프로젝트의 보안/개인정보 제약에
  적합한 설계.
- **COMA — 고전 앙상블 매칭**(Rahm & Bernstein 서베이): 문자열 유사도·동의어 사전·값 분포 유사도 등
  여러 매처를 앙상블로 결합. → LLM 호출 전 1차 저비용 필터로 쓰면 비용·속도·설명가능성에서 유리한
  하이브리드 구조 근거(§04 제안, 미착수).
- **US Patent 11,341,170 — 속성 정규화**: 제품 설명 텍스트에서 속성 후보를 추출해 "분류 트리 기반
  정규화기"로 표준화. → 여러 도매몰의 제각각 옵션명·카테고리명 정규화와 문제 정의가 거의 동일.

### 증분 동기화 (3단계 "연속관리")

- **SCD Type 2 — 스냅샷 diffing**([Airbyte: SCD Types](https://airbyte.com/data-engineering-resources/scd-types-in-data-warehouse)):
  소스 변경 로그에 접근 불가능할 때 쓰는 고전 패턴. 매 수집마다 현재 스냅샷을 가져와 직전 활성
  레코드와 필드별 diff → 변경분만 새 버전으로 upsert. → **스크래핑처럼 소스 로그 접근이 불가능한 이
  프로젝트에 정확히 맞는 CDC 대안** — Debezium류 로그기반 CDC는 적용 불가.
- **dbt incremental model (merge)**([dbt docs](https://docs.getdbt.com/docs/build/incremental-strategy)):
  `unique_key` 기반 멱등 upsert. → 스크래핑 재실행 시 중복 삽입을 막는 멱등성 설계의 표준 근거.

### 멀티채널 오픈마켓 아키텍처 (4단계)

- **Threecolts — "CommerceProvider" 패턴**([threecolts.com](https://www.threecolts.com/unicon)): 모든
  채널이 products/inventory/orders에 대해 동일한 계약(인터페이스)을 구현, 새 채널 추가는 "드라이버
  클래스 1개 + 매퍼 1개"로 끝남. → PTP의 `MarketplaceUploader` 인터페이스와 정확히 같은 설계 철학 —
  이미 올바른 방향으로 설계돼 있음.
- **플레이오토 — "마스터 상품 + 채널"**([plto.com](https://www.plto.com/)): 상품 등록 시 "마스터 상품"이
  먼저 생성되고 하위에 "쇼핑몰(채널)"을 추가하는 구조.
- **샵플링 — 표준카테고리 자동매핑**([shopling.co.kr](https://www.shopling.co.kr/)): 주요 마켓은
  사용자가 카테고리를 따로 만들 필요 없이 샵플링 표준카테고리로 자동 매핑.
- **AI 활용 사례**: Dalpha(신규 마트 상품 카테고리 자동분류), Intelligence Node(마켓플레이스 온보딩 시
  수천 SKU 자동 매칭), width.ai(Amazon 택소노미 4단계 깊이 92% 정확도 — 자사 발표치).

> **가장 위험한 실패모드**: Amazon Seller Central 가이드는 "잘못된 카테고리 템플릿에 업로드하면 하드
> 리젝 또는 **조용한 오매핑(silent attribute mapping)**으로 리스팅이 깨질 수 있다"고 명시적으로
> 경고한다. 이건 이 프로젝트의 AGENTS.md에 이미 기록된 "에러 없이 그럴듯한 값을 내는 폴백은 로그로
> 안 잡힌다"는 기존 사고 원칙과 정확히 같은 함정이다. 매핑/변환 로직을 검증할 때 "에러 유무"가 아니라
> "실제 산출물 값"을 픽스처로 대조하는 테스트를 반드시 둬야 한다.

**확인 안 됨으로 남긴 항목(설계 전 추가 검증 필요)**: Akeneo SDM의 "목표양식 업로드 → 자동 스키마
추론" 여부 / Flatfile "95% 자동매칭" 등 상용 제품의 정확도 수치(전부 자사 발표치) / Airbyte의 "AI
기반 매핑 제안"(공식 문서 기준 미확인) / 사방넷·플레이오토의 내부 알고리즘(보도자료 수준 정보뿐) /
ESM PLUS·11번가 API의 rate limit·승인절차 세부 / 키픽AI 내부 알고리즘(임베딩 기반인지 순수
프롬프팅인지), 속성 자동 매핑이 네이버 외 다른 마켓도 지원하는지.

## 04 · 설계 제안

원칙은 하나다 — **이미 있는 엔진(Transform, 연속관리, MarketplaceUploader 인터페이스)을 버리고 새로
만들지 않는다.** 세 조사 모두 "이미 올바른 방향으로 설계돼 있다"는 걸 확인했고, 비어있는 자리만
정확히 채우면 된다.

### 2단계 — 마이그레이션

1. **(a)와 (b)를 한 화면으로 합친다.** 지금처럼 "그리드 수동편집"(a)과 "Transform의 AI 컬럼규칙"(b)을
   별개 메뉴로 두지 말고, Transform 화면 자체를 "AI가 먼저 채운 매핑을 그리드에서 사람이 확정/수정"하는
   단일 흐름으로 통합한다. **(미착수)**
2. **"완성본 업로드로 스키마 역추론"은 1차 범위에서 제외하고 2차 옵션으로 분리한다.** 업계에 참고할
   안정 사례가 거의 없는 영역이라 리스크가 크다(열린 질문 2).
3. **카테고리 자동분류 AI를 추가한다.** ✅ `ca58cf8`.
4. **마이그레이션 AI 2곳을 멀티공급자 폴백에 연결한다.** ✅ `7ef4feb`.
5. **LLM 호출 앞에 저비용 1차 필터를 둔다.** COMA식 문자열/동의어 유사도로 명백한 매칭은 LLM 없이
