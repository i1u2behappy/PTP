# 작업 인수인계 (진행 중 작업 노트)

새 대화를 시작할 때 — 특히 `/clear` 직후 — **가장 먼저 읽는 문서**이고, 대화 맥락을 비우기 전에
**마지막으로 갱신하는 문서**입니다. 목적은 하나: 긴 대화에만 존재하던 상태를 여기에 옮겨 적어두고
대화를 비워도, 다음 세션이 코드와 커밋을 처음부터 다시 뒤지지 않고 이어서 일할 수 있게 하는 것.

## 다른 기록과 어떻게 나누나

| 어디 | 무엇을 담나 | 수명 |
| --- | --- | --- |
| 커밋 메시지 | 끝난 변경이 무엇이고 왜 그렇게 했는지 | 영구 |
| `!specifications/<기능>.md` | 기능/버그수정의 요구사항·설계 결정 | 영구 |
| **이 문서** | **아직 안 끝난 것 + 커밋에 안 남을 맥락** | **끝나면 지움** |

그래서 이 문서에는 "이미 커밋된 것이 무엇인지"를 옮겨 적지 않습니다 — `git log`가 더 정확하고 더
자세합니다. 작업이 커밋되면 해당 항목을 여기서 **지우고**, 영구히 남길 설계 결정이 있으면 그때
스펙 문서로 옮깁니다. 이 문서가 계속 짧아야 `/clear` 직후에 읽는 비용이 작습니다.

## 갱신 규칙

- 대화 맥락을 비우기 전에 아래 세 절(진행 중 / 다음 할 일 / 최근 맥락)을 현재 상태로 갱신한다.
- 한 항목은 **다음 세션이 그것만 읽고 이어서 손댈 수 있을 만큼** 구체적으로 적는다 — 건드린 파일
  경로, 지금까지 확인된 사실, 아직 확인 못 한 것, 다음 한 걸음.
- 확인한 사실과 추정을 구분해서 적는다. 추정을 사실처럼 적으면 다음 세션이 그걸 근거로 잘못된
  방향으로 한참 갈 수 있다.
- 날짜는 "어제/지난주"가 아니라 절대날짜로 적는다(이 문서를 읽는 시점이 언제일지 모름).

     동작이 이제 화면에 드러난다.
  5. **추출이 사이트 공통 메타로 샘** — 상품 상세페이지인데 og:title/og:image가 몰 이름·로고인 몰
     (투비즈온). 본문 상품명(`h3.product-name` 등)을 og보다 먼저 보도록 순서를 뒤집고, og:image는 마지막
     폴백으로 내렸다. 실제 페이지 HTML로 확인: 상품명 "여성 오버핏 체크 리버시블 자켓…", 이미지 `/goods/…`.

  6. **표본 수집에 안정화 대기가 없었다** — 개수 세기에만 넣고 수집엔 안 넣어, 정렬 클릭이 없는 실행은

     없는 실행 4초 실패). `collectFromListing`의 1페이지 스캔에 같은 대기를 넣어 해결.
  7. **상품코드/카테고리/설명/옵션 오염** — 실제 세션으로 직접 돌려 필드별로 확인하고 고쳤다:
     상품코드가 URL 전체(→ 파라미터 이름 규칙으로 `goodscd` 등 일반화), 몰카테고리에 드롭다운 메뉴가
     통째로(→ 보이는 `<li>`만 + "○분류 선택" 플레이스홀더 제외), 추가설명이 메타 키워드(→ 본문 우선),
     옵션1이 카테고리 체크박스 `cate[]`(→ OPTION_SELECT_EXCLUDE_RE에 cate/category/분류/검색/브랜드 추가).
  8. **페이지 번호가 URL 해시에 실리는 몰 지원** — 이 몰은 `#page=2&category=007`로 페이지를 넘긴다.
     `withPageParam`이 해시도 다루게 하고, 해시만 바뀌면 문서를 다시 안 읽는 문제(same-document)를
     새로고침으로 처리. 실측: 같은 URL에 `#page=1`/`#page=2`를 주면 실제로 다른 상품이 나온다.
  9. **미리보기는 빠르게, 정확한 값은 전용 버튼으로**(사용자 지시) — `PREVIEW_PAGE_BUDGET`(5페이지)을
     두고 예산에 닿으면 `truncated`로 "N개 이상" 표시. 카테고리당 97초 → 37초.

  **아직 안 끝난 것(다음 세션이 이어서 할 일) — 가장 중요**:
  - ⚠ **"정확한 총 개수 확인"이 아직 정확하지 않다.** 해시 페이징을 지원한 뒤 24개에서는 벗어났지만
    (40페이지 한도 → 404개, 100페이지 한도 → 1,004개) **한도에 정비례해 늘어난다 = 끝을 못 찾는다.**
    게다가 페이지당 고유 상품 수가 안 맞는다: 1페이지는 20개인데 그 뒤는 페이지당 ~10개(개수 세기 쪽은
    1페이지를 24개로 본다). 페이지 간 상품이 겹치는 것으로 의심된다.
    **다음 한 걸음**: 렌더링이 끝난 2페이지 DOM을 직접 떠서 1페이지와 상품 URL 집합을 대조한다. 겹치면
    해시 이동만으로는 목록이 완전히 갱신되지 않는다는 뜻이므로, 앞서 찾아둔 **POST 폼**(`cfrm`/`sfrm`의
    hidden 필드 `ctno`/`page`/`category`)으로 페이지를 넘기는 방식으로 바꿔야 한다.
    참고: `fetchPageText`는 AJAX 렌더 전 HTML을 돌려줘 상품 링크가 0개다 — 렌더 후 스냅샷이 필요하면
    대기를 넣거나 previewCatalog 경로로 확인할 것.
  - 개발자모드(확장)에는 `categorySortClicks` 적용 경로가 아예 없다(정렬 무시) — 알려진 갭.

- **운영 메모**: 워커를 dev 서버 감시자가 아니라 **직접 기동**해둔 상태라 로그가 `.worker.log`가 아니라
  스크래치패드 임시 파일로 갈 수 있다. 다음 세션에서 로그가 안 보이면 PTP 화면의 "워커 재시작"을 한 번
  눌러 정상 경로로 되돌릴 것.

## 자주 쓰는 절차

매번 다시 찾게 되는 것만 모았습니다. 규칙(검증 루프, 교차모드 확인 등)은 루트 `AGENTS.md`가 기준입니다.

- **검증 루프**: `npx tsc --noEmit` → `npm run lint` → `npm run test:unit` (통과할 때까지 스스로 고친다)
- **dev 서버**: `npm run dev` / 재시작 `scripts/restart-dev-server.ps1` / `.next` 캐시까지 버리려면 `npm run dev:clean`
- **워커**: `npm run worker` — `worker/`나 워커가 쓰는 `lib/` 소스를 고쳤으면 **재시작해야 반영된다.**
  고쳤는데 동작이 그대로면 재시작 여부부터 확인할 것.
- **개발자모드 확장**(`extension-poc/`): 고친 뒤 `chrome://extensions`에서 **서비스워커를 리로드해야
  반영된다.** 위와 같은 이유로, 증상이 안 바뀌면 리로드부터 의심.
- **DB**: Docker 컨테이너 `scrape-postgres`(호스트 포트 `5433`). 페이지가 빈 목록이거나 API가 500이면
  코드 버그로 단정하기 전에 `docker ps`로 `Up` 확인 (자세한 내용은 루트 `README.md`).
