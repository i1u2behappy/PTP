# 작업 인수인계 (진행 중 작업 노트)

새 대화를 시작할 때 — 특히 `/clear` 직후 — **가장 먼저 읽는 문서**이고, 대화 맥락을 비우기 전에
**마지막으로 갱신하는 문서**입니다. 목적은 하나: 긴 대화에만 존재하던 상태를 여기에 옮겨 적어두고
대화를 비워도, 다음 세션이 코드와 커밋을 처음부터 다시 뒤지지 않고 이어서 일할 수 있게 하는 것.

## 다른 기록과 어떻게 나누나

| 어디 | 무엇을 담나 | 수명 |
| --- | --- | --- |
| 커밋 메시지 | 끝난 변경이 무엇이고 왜 그렇게 했는지 | 영구 |
| `!specifications/<기능>.md` | 기능/버그수정의 요구사항·설계 결정 | 영구 |
| **이 문서** | **아직 안 끝난 것 + 커밋에 안 남을 맥락** | **끝나면 지움** |

그래서 이 문서에는 "이미 커밋된 것이 무엇인지"를 옮겨 적지 않습니다 — `git log`가 더 정확하고 더
자세합니다. 작업이 커밋되면 해당 항목을 여기서 **지우고**, 영구히 남길 설계 결정이 있으면 그때
스펙 문서로 옮깁니다. 이 문서가 계속 짧아야 `/clear` 직후에 읽는 비용이 작습니다.

## 갱신 규칙

- 대화 맥락을 비우기 전에 아래 세 절(진행 중 / 다음 할 일 / 최근 맥락)을 현재 상태로 갱신한다.
- 한 항목은 **다음 세션이 그것만 읽고 이어서 손댈 수 있을 만큼** 구체적으로 적는다 — 건드린 파일
  경로, 지금까지 확인된 사실, 아직 확인 못 한 것, 다음 한 걸음.
- 확인한 사실과 추정을 구분해서 적는다. 추정을 사실처럼 적으면 다음 세션이 그걸 근거로 잘못된
  방향으로 한참 갈 수 있다.
- 날짜는 "어제/지난주"가 아니라 절대날짜로 적는다(이 문서를 읽는 시점이 언제일지 모름).

  재시작이 사용자의 진행 중 작업을 끊음) — 실제로 두 번 겪었다. 재발 방지 규칙을 Claude 개인 메모리에
  남겼다(`feedback_no_live_site_collision.md`) — 요지: 실제 siteId로 라이브 테스트 전엔 그 몰이 지금
  화면에서 쓰이고 있는지 먼저 확인하고, `maxPages` 같은 작은 상한으로 먼저 검증한다.
- 도매창고 실측(2026-09-26): MD추천 카테고리 총 356개, 20개/페이지 → 18페이지. 페이지네이션은
  `<div class="num" data-page="N">` 클릭+AJAX 전용 — `?page=N` 쿼리파라미터는 서버가 완전히
  무시한다(직접 확인: `?page=2`로 이동해도 pager는 여전히 1페이지를 `cur`로 표시). 플랫폼은
  `scrape_profile.platform: "unknown"`(고도몰 등 알려진 플랫폼 아님).
- Groq 계정이 이 세션 중 실제로 레이트리밋(429, `ITPM 7000, Used 6930`)에 걸리는 걸 직접 확인함 —
  기존에 알던 8000 TPM(다른 한도 종류) 제약과는 별개로 ITPM(분당 입력 토큰) 한도도 실재한다.
- Gemini도 이 세션 중 한 번 503(과부하)로 실패하는 걸 직접 확인함 — 폴백 체인(Anthropic→Gemini→Groq→
  Ollama)이 실사용에서 실제로 여러 단을 거쳐 내려가는 걸 로그로 확인.
- 도매창고(site 29)·걸스굽(site 1) 둘 다 이번에 발견된 문제의 재현·검증에 실사용 중인 사이트임 —
  둘 다 로그인 불필요(`manual_login_required=false`, 일반모드).
- 워커 재시작(`npm run restart-worker`, schtasks 기반)이 이 세션 중 한 번 비정상적으로 오래 걸렸다
  (10~30초 예상 vs 실제 관측 최대 ~150초, 원인 미확인 — schtasks 자체 지연으로 추정, 재현 안 해봄).
  워커가 하나도 안 뜬 채로 방치되는 상황도 한 번 있었는데, 그때는 `npm run worker`를 백그라운드로 직접
  실행해 복구했다(정식 restart-worker 스크립트가 안 먹힐 때의 임시 우회로 유효함을 확인).

> 적을 내용 예: 실측 수치(어떤 조건에서 몇 초 걸렸는지), 해봤다가 접은 접근과 그 이유, 사용자가
> 내린 결정과 그 근거, 재현은 됐는데 원인을 아직 못 찾은 현상.

## 자주 쓰는 절차

매번 다시 찾게 되는 것만 모았습니다. 규칙(검증 루프, 교차모드 확인 등)은 루트 `AGENTS.md`가 기준입니다.

- **검증 루프**: `npx tsc --noEmit` → `npm run lint` → `npm run test:unit` (통과할 때까지 스스로 고친다)
- **dev 서버**: `npm run dev` / 재시작 `scripts/restart-dev-server.ps1` / `.next` 캐시까지 버리려면 `npm run dev:clean`
- **워커**: `npm run worker` — `worker/`나 워커가 쓰는 `lib/` 소스를 고쳤으면 **재시작해야 반영된다.**
  고쳤는데 동작이 그대로면 재시작 여부부터 확인할 것. `npm run restart-worker`가 안 먹히거나 너무
  오래 걸리면, `npm run worker`를 직접 백그라운드로 띄우는 것도 유효한 임시 우회다(2026-09-26 확인).
- **라이브 사이트 테스트 전엔 항상 먼저 확인**: `tasklist`/`wmic`로 `.playwright-profiles\<siteId>`
  프로필을 쓰는 `chrome.exe`가 이미 떠 있는지(=그 몰을 화면에서 지금 쓰고 있을 가능성) 확인하고,
  `maxPages` 등 작은 상한으로 먼저 검증한다(2026-09-26 사고 이후 규칙, 위 "최근 맥락" 참고).
- **개발자모드 확장**(`extension-poc/`): 고친 뒤 `chrome://extensions`에서 **서비스워커를 리로드해야
  반영된다.** 위와 같은 이유로, 증상이 안 바뀌면 리로드부터 의심.
- **DB**: Docker 컨테이너 `scrape-postgres`(호스트 포트 `5433`). 페이지가 빈 목록이거나 API가 500이면
  코드 버그로 단정하기 전에 `docker ps`로 `Up` 확인 (자세한 내용은 루트 `README.md`).
